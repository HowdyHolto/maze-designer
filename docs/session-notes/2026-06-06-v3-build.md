# Session Notes — 2026-06-06 — v3 Full Build

## Session overview
Extended build session in Claude.ai chat, starting from v2 (prior session) and building through v3.3. Covers the full redesign to a 4-step flow, door placement system, tool preset cascade, constraint system, and multiple bug fix rounds.

---

## What was built this session

### 4-step UX flow
Replaced the old 3-tab layout (Boundary / Generate / Export) with:
```
1 · Boundary  →  2 · Doors & Path  →  3 · Generate  →  4 · Export
```
Step tabs are gated — Doors unlocks after boundary is set, Generate after Doors, Export after maze is generated. Each step has a "Next →" button at the bottom.

### Door placement system (Step 2)
- Preview grid is built from the current boundary + cellSize
- Perimeter faces computed: every inside cell face pointing toward outside/off-grid
- Rendered as small hollow circles on canvas in Doors step
- Click to snap to nearest face (no distance threshold — always snaps nearest)
- Entry = green dot + outward tick mark
- Exit = orange dot + outward tick mark (or interior dot for interior finish mode)
- **exitMode**: 'perimeter' (both on edge) or 'interior' (entry on edge, finish anywhere inside)
- Auto-advances placing state: after entry set → placing='exit', after exit set → placing=null

### Door persistence — mm-coordinate system
**Critical architecture decision**: doors are stored with BOTH col/row AND mx/my (world mm).
On every `doGenerate()` call, the preview grid is rebuilt and doors are re-snapped using mx/my,
not col/row. This fixes the bug where changing cellSize between door placement and generation
would cause doors to point to wrong/nonexistent cells.

### Custom path (Step 2)
- Checkbox in Doors step reveals path drawing mode
- Hold and drag on canvas → freehand path → RDP simplification → BFS snap to grid
- Path auto-starts at entry door position (on mousedown)
- Path auto-ends at exit door position (appended to raw points before snapping)
- Stored as `S.doors.pathCells` — fed to genOrtho as forced DFS seed

### Tool preset cascade (Step 3)
Four tool types: CNC Router/End Mill, Laser Cutter, 3D Printer/Nozzle, Ball/Marble Maze
Each type has size dropdown (e.g., 1/16", 1/8", 1/4" for mill) that cascades:
- `toolDiamMm` → `constraints.minP` (min passage) + `constraints.minW` (min wall)
- `constraints.minC` = minP + minW (min cell size)
- `cellSize` raised to meet minC if needed
- `wallFrac` set to tool default
- `kerf` set appropriately

### Constraint validation (right panel, always visible)
Shows tool diameter, min passage, actual passage, actual wall in real mm.
Green "Constraints met" or yellow warning if below minimum.

### Auto-solve after generation
When doors are set, `solveMaze()` is called automatically after `doGenerate()`.
User immediately sees solution path without needing to click Solve manually.

### Visibility layers (right panel, post-generation)
All layer toggles moved to right panel:
- Boundary, Walls, Doors, Grid overlay
- Solution (purple), Dead ends (coral, with branch sub-list), Alternates (light purple)

### Saved boundaries
localStorage persistence. Up to 8 saved boundaries by name.
Save button appears once a boundary is confirmed; named entries appear below.

### "Are you sure" modal
`confirmIfMaze(msg, cb)` — shows modal if maze exists, calls cb directly otherwise.
Triggered by: Generate (second time), boundary change, grid type change.

## Bugs fixed this session

### JS syntax error (black screen)
Previous version used ES6 template literals with nested `${}` in single-quoted strings.
Browser couldn't parse → silent black screen. Fix: rewrote all UI render functions using
string concatenation with explicit escaped quotes in onclick handlers.

### Door placement not working
Three root causes:
1. `rebuildDoorState()` called `clearDoors()` which reset `placing=null` — fix: keep placing
2. `handleDoorClick` used stale `_hoverFace` — fix: compute nearest face fresh from `S.mw`
3. Distance threshold on `nearestFace` was too tight — fix: removed threshold entirely

### BFS in solveMaze broken
`Object.keys(DIRS).forEach(function(d){ ... })` with `var cur` inside while loop — var hoisting
caused the BFS to not traverse correctly. Fix: complete rewrite with explicit `for` loops,
plain `{}` objects for visited/dist/prev (not Map/Set), distinct variable names at each scope.

### Regenerate not honoring doors (v1 fix)
`S._modalOk` callback correctly called `doGenerate()`, but door col/row positions could
become stale if cellSize changed. Fix: mm-coordinate re-snapping system (see above).

### Regenerate not honoring doors (v2 fix — deployed)
Further hardening: `doGenerate()` now:
1. Extracts `mx/my` from current doors before ANY reset
2. Rebuilds preview grid with current settings
3. Calls `snapFaceFromMm()` to re-derive col/row from mm positions
4. Stores fresh door objects back to `S.doors.entries/exits`

### Custom path: not starting at entry
`startPathDraw()` was starting from raw mouse position. Fix: start from `entries[0].mx/my`
if entry is set, so path always originates at the entry door.

### Custom path: not ending at exit
`finishPathDraw()` was snapping only the drawn points. Fix: append `exits[0].mx/my` to
raw path points before snapping, so path always terminates at exit door cell.

### Ghost line polygon fix
Polygon boundary drawing was only showing rubber-band line after 2nd click.
Fix: show ghost line from first point onward (no minimum).

## Architecture decisions

### `cellKey(col, row)` → `"col,row"`
Simple string concatenation, used everywhere for cmap lookups.
Both col and row are always integers. No floating point keys.

### Plain objects for BFS maps
`var visited = {}`, `var dist = {}`, `var prev = {}` — faster and no closure issues
compared to `new Map()` / `new Set()` inside callback-heavy BFS.

### `doGenerate()` vs `generateMaze()`
`generateMaze()` just calls `confirmIfMaze(..., doGenerate)`.
All actual logic in `doGenerate()`. Never call `genOrtho()` directly.

### Door arrays support multiple doors
`S.doors.entries` and `S.doors.exits` are arrays even though UI only sets one each.
Multi-door support is a UI change only — architecture is already extensible.

### No build system
Single `index.html` file. No npm, no webpack, no dependencies.
Deliberate choice for simplicity and portability. Keep it this way.
