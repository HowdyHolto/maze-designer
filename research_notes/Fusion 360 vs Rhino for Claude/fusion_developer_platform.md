## 1. Fusion desktop API (Python / C++ / TypeScript scripts and add-ins): how code runs, Python version, packages, storage, external triggering

### Takeaway
The desktop Fusion API runs only *inside a live, logged-in Fusion GUI session* — there is no CLI, no headless mode, and no official command-line or external-process entry point; the officially sanctioned "external" paths are (a) an add-in you write that opens its own socket/HTTP listener and marshals work to Fusion's main thread via custom events, (b) the `fusion360://` URL handler for opening/inserting files, and (c) since 2026, Autodesk's own local **Fusion MCP server** (Preferences > General > API, default port 27182). Fusion currently embeds **Python 3.12**, with Autodesk announcing a move to **3.14** in a "January release"; the API is also exposed to C++ and (newer) TypeScript. There is no pip integration; packages are vendored into the add-in folder or installed by calling Fusion's bundled interpreter.

### Cited Findings
**How scripts/add-ins run**
- Fusion creates scripts in a "Scripts" subdirectory and add-ins in an "AddIns" subdirectory under a default API folder; the default path is editable under Preferences > General > API; Fusion only auto-searches the default locations and anything elsewhere must be registered with the green "+" icon in the Scripts and Add-Ins dialog — [Fusion API User Manual: Writing & Debugging](https://help.autodesk.com/cloudhelp/ENU/Fusion-360-API/files/WritingDebugging_UM.htm)
- A community README gives the Windows add-in path as `%APPDATA%\Autodesk\Autodesk Fusion 360\API\AddIns` — [jon-harper/Clock3Scripts](https://github.com/jon-harper/Clock3Scripts); the API's `ApplicationFolders.userDataPath` property returns "the path where user-specific data such as add-ins, scripts, and custom content is stored" — [ApplicationFolders Object](https://help.autodesk.com/cloudhelp/ENU/Fusion-360-API/files/ApplicationFolders.htm)
- Autodesk's `ScriptSourceLocations` enumerator distinguishes App Store add-ins (Windows `%appdata%\Autodesk\ApplicationPlugins`, Mac `~/Library/Application Support/Autodesk/...`) from non-App-Store add-ins — [ScriptSourceLocations Enumerator](https://help.autodesk.com/cloudhelp/ENU/Fusion-360-API/files/ScriptSourceLocations.htm) (search extraction also named `%appdata%\Autodesk\FusionAddins`; path naming could not be verified directly — see Gaps)
- "Run on Startup" is add-in-specific (not available for scripts): it "indicates if the add-in should be run automatically when Fusion is started"; exposed in the API as `Script.isRunOnStartup` — [Writing & Debugging](https://help.autodesk.com/cloudhelp/ENU/Fusion-360-API/files/WritingDebugging_UM.htm); [Script Object](https://help.autodesk.com/cloudhelp/ENU/Fusion-360-API/files/core_Script.htm); an Autodesk staffer explained a non-auto-starting project was failing because its manifest declared `"type": "script"` — [Forum: Run on startup](https://forums.autodesk.com/t5/fusion-api-and-scripts-forum/run-on-startup/td-p/7226109) **[older]**
- Asked whether a command-line invocation could run a Python file that models in Fusion, forum answers (2023) say the options are Python scripts/add-ins or the Text Commands window inside Fusion; running "from pure Python or the command line outside Fusion will need further development" — i.e. Fusion must be open — [Forum: execute a command from the command line](https://forums.autodesk.com/t5/fusion-api-and-scripts-forum/is-it-possible-to-execute-a-command-from-the-command-line-that/m-p/12265338)
- An Autodesk developer stated an add-in cannot launch a script or run one by name ("impossible") — [Forum: Run addin from script](https://forums.autodesk.com/t5/fusion-api-and-scripts/run-addin-from-script/td-p/7728909) **[older]**
- Importing the `adsk` modules into an external Python does not work; API code "has to run inside Fusion's own Python"; the bundled interpreter lives under a hashed folder in `AppData\Local\Autodesk\Webdeploy\Production\<hash>` whose location changes per Fusion version — [Forum: Where are the Fusion 360 modules located?](https://forums.autodesk.com/t5/fusion-api-and-scripts-forum/where-are-the-fusion-360-modules-located/td-p/7041901) **[older]**

**Python version**
- Autodesk developer blog: "the Python version used in Fusion is being upgraded from 3.12 to 3.14" in "the January release"; add-ins shipped as compiled `.pyc` built for 3.12 will fail to load on 3.14, while `.py` source is unaffected; developers shipping `.pyc` should regenerate them with an Insider build of the January release; the same post says Intent-Driven Design becomes enabled for everyone in that release — [Fusion Python Upgrade and more (blog.autodesk.io)](https://blog.autodesk.io/fusion-python-upgrade-and-more/) (no year visible in extraction; see Gaps)
- Earlier official notices: embedded Python moved 3.7 → 3.9.7 (2022-era thread), with the same `.pyc` incompatibility warning — [Forum: Important Python Version Change Information](https://forums.autodesk.com/t5/fusion-api-and-scripts-forum/important-python-version-change-information/td-p/10929351) **[older]**; the third-party `apper` framework docs still say "Fusion 360 uses Python 3.7" — [apper docs](https://apper.readthedocs.io/en/latest/usage/installation.html) **[stale]**

**Installing packages (pip)**
- No official Autodesk guidance on dependency management was found. Community approaches: (a) run Fusion's own interpreter via `subprocess.check_call([sys.path[0] + '\Python\python.exe', "-m", "pip", "install", 'scipy'])` from inside a script (reported working after a path fix); (b) the "correct way" per a thread contributor: create a `./lib` folder inside the add-in, `pip download` wheels for each target platform (`--platform win_amd64`, manylinux, macOS), extract them there and add that folder to `sys.path` — [Forum: numpy/scipy in Fusion scripts](https://forums.autodesk.com/t5/fusion-api-and-scripts-forum/how-to-use-modules-like-numpy-scipy-etc-by-conda-in-fusion-360/td-p/9355499); [Forum: To install Python modules](https://forums.autodesk.com/t5/fusion-api-and-scripts-forum/to-install-python-modules/td-p/5777176)
- Installing into a *global* Python environment does not work because the add-in loads packages from Fusion's Webdeploy folder (`ImportError` reported) — [same thread](https://forums.autodesk.com/t5/fusion-api-and-scripts-forum/to-install-python-modules/m-p/10823658/highlight/true)

**Languages**
- C++: creating a C++ script/add-in generates one `.cpp` plus both a Visual Studio `.vcxproj` and an Xcode `.xcodeproj`; the binary Fusion loads is OS-specific; debugging is OS-specific; code is portable unless it uses OS-specific libraries — [C++ Specific Issues](https://help.autodesk.com/cloudhelp/ENU/Fusion-360-API/files/CPPSpecific_UM.htm); Autodesk's tutorial uses Visual Studio 2022 (Windows) and Xcode 16 (macOS) — [My First Fusion Plug-in Overview](https://blog.autodesk.io/my-first-fusion-plug-in-overview/)
- TypeScript: desktop scripts import from `@adsk/fusion`; cloud (Automation API) scripts import from `@adsk/fusion/automation`, which has "network and file I/O only, no UI access" — [TypeScript Specific Issues](https://help.autodesk.com/cloudhelp/ENU/Fusion-360-API/files/TypeScriptSpecific_UM.htm)
- Autodesk's official sample repository is documented in the API manual — [Using Samples from GitHub](https://help.autodesk.com/cloudhelp/ENU/Fusion-360-API/files/UsingSamplesFromGitHub_UM.htm)

**Triggering from an external process**
- `fusion360://` protocol handler: Fusion registers it at install; a link such as `fusion360://host/?command=open&file=...` opens the file as a new design or inserts it as a component; Fusion starts if not running; the browser shows a security prompt on first use — [Opening Files from a Web Page](https://help.autodesk.com/cloudhelp/ENU/Fusion-360-API/files/OpeningFilesFromWebPage_UM.htm) **[older page]**
- Autodesk forum guidance for driving Fusion from POST requests: run the listener on a separate thread and use custom events to pass work back to Fusion's main thread — [Forum: Changing dimensions of a model from POST requests](https://forums.autodesk.com/t5/fusion-api-and-scripts-forum/changing-dimensions-of-a-model-from-post-requests/m-p/8604371/highlight/true) **[older]**
- Community pattern (not official): an add-in starts an HTTP server in a thread; external code calls e.g. `GET http://127.0.0.1:18080/cmd?edge=50`; every command is marshalled through a `CustomEvent` because the modeling API must run on the main thread — [LiveCube add-in README](https://glama.ai/mcp/servers/@sockcymbal/autodesk-fusion-mcp-python/blob/a3398ac5c76baa252240f301167a4cba2fe6f5b8/README.md); [adom-desktop-fusion-bridge](https://wiki.adom.inc/kyle/adom-desktop-fusion-bridge)
- **Official local MCP (2026):** Autodesk's Claude Desktop connector guide says to enable "Fusion MCP Server" in Fusion's API preferences and install the connector from Claude Desktop's connector directory; the port "matches the one from Fusion's API Preferences (27182 by default)" — [How to improve your Fusion workflow with the Claude Desktop connector](https://www.autodesk.com/products/fusion-360/blog/how-to-improve-your-fusion-workflow-with-the-claude-desktop-connector/); a separate Autodesk post describes using the Fusion MCP to have an agent write add-ins — [Build Your Own Fusion Add-ins with the Fusion MCP](https://www.autodesk.com/products/fusion-360/blog/build-your-own-fusion-add-ins-with-the-fusion-mcp/); Autodesk's MCP documentation hub — [Autodesk MCP Server Documentation](https://help.autodesk.com/view/ADSKMCP/ENU/). (Depth on MCP servers is covered by another researcher.)

### Inferences
- For Claude Code on the user's machine: the only robust path is to have Fusion open and either (a) use Autodesk's local Fusion MCP server (first-party, port 27182) or (b) install a small Python add-in with "Run on Startup" that listens on localhost and executes API code via custom events — exactly the community bridge pattern. Claude Code can write files into `%APPDATA%\Autodesk\Autodesk Fusion 360\API\AddIns` (or the macOS equivalent), but a human must still enable the add-in once in the Scripts and Add-Ins dialog.
- For Claude Code in a cloud Linux container: the desktop API is unusable (no Linux build, no headless mode). Only the cloud APIs in §2 apply.
- Because the `.pyc` incompatibility recurs with every embedded-Python bump (3.7→3.9→3.12→3.14), any add-in Claude Code writes should ship `.py` source only and vendor pure-Python or per-platform wheels in `./lib`.
- The TypeScript surface matters for a Node-capable agent: desktop TypeScript scripts (`@adsk/fusion`) and cloud Automation scripts (`@adsk/fusion/automation`) share an API shape, so code can be prototyped locally and moved to the cloud.

### Gaps
- Could not read the Autodesk API manual pages directly (egress block), so the exact default macOS script path and the exact wording about `%appdata%\Autodesk\FusionAddins` vs `...\Autodesk Fusion 360\API\AddIns` are unverified; both strings appeared in extractions.
- The year of the "3.12 → 3.14 in the January release" post is not visible in search extractions. Python 3.14.0 shipped in October 2025, so this most plausibly refers to the January 2026 or January 2027 Fusion release; as of Oct 2026 Fusion should be treated as **3.12 now, 3.14 imminent or already shipped** — verify in Fusion via `sys.version`.
- No official Autodesk document was found stating whether Text Commands can be fed from stdin or a file at launch; the forum consensus (2023) is no.

## 2. Headless and cloud options: Fusion Automation API, APS (Manufacturing Data Model, Data Management, Model Derivative, Design Automation), Fusion Compute MCP — status, auth, cost

### Takeaway
Autodesk now offers a genuinely headless Fusion: the **Fusion Automation API** (GA 19 May 2025; TypeScript scripts run in a cloud sandbox; Premium API billed at 3.0 Flex tokens per processing hour, ≈ US$9/hour at the ~$3/token list rate) and, since 2026, a cloud-hosted **Fusion Compute MCP** (public beta/tech preview; sessions up to one hour; modeling, CAM setups/toolpaths/NC post, STL/STEP export). Read-only/data access is via the GraphQL **Manufacturing Data Model API** (v3 GA Sept 2025; paid pricing from 17 Aug 2026 with subscription-included quotas) and **Model Derivative** (translates `.f3d` → STEP/IGES/OBJ/STL/DWG/FBX/SVF2). All require an APS app (OAuth 2.0, 2-legged and/or 3-legged) in the same Autodesk team as the Fusion subscription; PAT auth for Automation is deprecated (removal 3–6 months after 29 Jul 2026).

### Inferences
- For a Claude Code agent in a cloud Linux container this is the *only* way to touch Fusion: register an APS app, obtain 2LO (and, for the user's own hub, 3LO) tokens, upload STEP/DXF/SVG or a TypeScript script via Data Management / Automation API, and read results back. Expect ≈3 Flex tokens (~US$9) per processing hour for Automation jobs, metered to the second including file transfer, plus whatever Fusion/APS entitlement is required.
- Model Derivative gives a clean one-way bridge `.f3d → STEP/OBJ/STL/DWG` without Fusion running, which is useful for *reading* existing Fusion designs, but it cannot create or modify `.f3d`.
- The Compute MCP is the lowest-friction headless route for an agent (natural MCP client, no TypeScript), but it is beta and Autodesk's own messaging about which clients are supported is inconsistent across posts (see Gaps).

### Gaps
- Whether the Fusion Automation API, Compute MCP, or included API quotas are available to **Fusion for Personal Use** accounts was not found in any source; the subscription-inclusion posts only say "qualifying/eligible" subscriptions. Treat as "paid-only until proven otherwise."

- Model Derivative support for `.f3z` (multi-file archive) was not confirmed; only `.f3d` appears in the table.
- Session count limits for Compute MCP (a third-party guide claimed two concurrent one-hour sessions) were not confirmed on Autodesk pages.
- Pricing of the Compute MCP after beta is unknown.

## 3. File formats: what Fusion imports/exports, Rhino `.3dm`, SVG and DXF import behavior and documented limitations

### Takeaway
Fusion's "Standard" formats (all license types, including Personal Use) cover 3MF, f3d, Inventor, DXF, FBX, IGES, JT, OBJ, SketchUp, SMT, STEP, STL and USDZ; "Additional" formats (DWG, SAT/SMT ≤ ACIS v7, Rhino `.3dm`, CATIA V5, NX, Parasolid, etc.) are import-only and **not available to Personal Use**. Rhino `.3dm` is importable (not exportable) on paid licenses. SVG import is the weakest link for the user's maze app: Fusion treats unitless SVG pixels at 96 dpi, discards stroke width and fill, flattens everything to sketch curves (one sketch), requires text to be pre-converted to paths, and has a known double-scale bug; large files (~18k curves) overwhelm the sketch solver. DXF import is better behaved: layers map to separate sketches (optional), units must be chosen in the dialog (default cm), and splines come in as non-editable fixed splines unless the API option is set.

### Cited Findings
**Format lists**
- Standard tier ("supported for all license types"): 3MF, Autodesk Fusion (*.f3d), Inventor (*.iam, *.ipt), DXF, FBX, IGES, JT, OBJ, SketchUp, SMT, STEP, STL, USD (*.usdz); Additional tier ("all license types except Personal Use"): AutoCAD DWG, SAT/SMT, CATIA V5, NX, Parasolid, Rhino (*.3dm), others; "Fusion only supports up to ACIS version 7"; Rhino's export column is blank — [Supported file formats (Fusion help)](https://help.autodesk.com/cloudhelp/ENU/Fusion-Import/files/TPD-SUPPORTED-FILE-FORMATS.htm); mirrored at [Fusion-Designs](https://help.autodesk.com/cloudhelp/ENU/Fusion-Designs/files/TPD-SUPPORTED-FILE-FORMATS.htm)
- Export via File > Export; some types require cloud translation; exportable types include DWG, DXF, IGES, SAT, SMT, STEP, STL, OBJ — [How to export a design in Fusion (Autodesk support)](https://autodesk.com/kr/support/technical/article/How-to-export-a-design-in-Fusion-360); API `ExportManager` object — [ExportManager](https://help.autodesk.com/cloudhelp/ENU/Fusion-360-API/files/fusion_ExportManager.htm)
- Older Autodesk post: Data Panel uploads of Rhino `.3dm` go through the Autodesk Translation Service for native editing — [Data exchange in Fusion 360 part 1](https://www.autodesk.com/products/fusion-360/blog/data-exchange-in-fusion-360-part-1/) **[older]**
- Third-party converters confirm `.3dm` opens in Fusion and recommend STEP/IGES/OBJ/FBX for Fusion→Rhino — [CAD Exchanger](https://cadexchanger.com/3dm-to-fusion-360/); [Okino](https://www.okino.com/convert/fusion/fusion_to_rhino.htm)

**SVG import behavior (Insert > Insert SVG)**
- Fusion imports SVG pixels at 96 dpi ("Fusion 360 imports SVGs at 96 dpi, while A.I. saves SVGs at 72 dpi"); workaround scale factors 1.333 (Illustrator) or 3.779528 (Inkscape px→mm) in the insert dialog; a moderator states "1mm in an SVG file transforms to 1mm in Fusion as long as the SVG is saved in mm instead of pixels" — [Forum: SVG scale is wrong](https://forums.autodesk.com/t5/fusion-360-design-validate/svg-scale-is-wrong/td-p/6560352); [Forum: Import SVG scale](https://forums.autodesk.com/t5/fusion-design-validate-document/import-svg-scale/m-p/5950348); [Forum: Fix dimensions of imported SVG?](https://forums.autodesk.com/t5/fusion-support-forum/fix-dimensions-of-imported-svg/m-p/13915953)
- Reported bug: the dialog's scale option is applied twice; workaround is to import then scale the sketch — [Forum: Fix dimensions of imported SVG?](https://forums.autodesk.com/t5/fusion-support-forum/fix-dimensions-of-imported-svg/m-p/12481033)
- Fusion cannot scale an imported SVG to an exact dimension at import, only proportionally; afterwards unlock the sketch and apply a dimension — [Inkscape forum tip](https://inkscape.org/forums/tutorials/fusion-360-svg-import-scaling-by-dimension-tip)
- Autodesk staff: Fusion imports SVG "as sketch curves", does not support a width attribute so "all you see is the centerline", and "there is no guarantee that Fusion will render an SVG exactly as other applications" — [Forum: SVG Import Handling](https://forums.autodesk.com/t5/fusion-support-forum/svg-import-handling/m-p/9744571/highlight/true)
- Text must be converted to paths before export; "Fusion can only recognize curves in an SVG"; no native text-on-path — [Forum: Curved Text](https://forums.autodesk.com/t5/fusion-design-validate-document/curved-text/m-p/6323897/highlight/true)
- Imported SVG geometry arrives locked/fixed and hard to select; a "dirty" SVG with gaps causes failures — [Forum: Why can't I insert an SVG?](https://forums.autodesk.com/t5/Fusion-Design-Validate-Document/Why-can-t-I-insert-an-SVG-/td-p/9759030); user reports of 250× size errors from CorelDraw exports — [Forum: svg](https://forums.autodesk.com/t5/fusion-design-validate-document/svg/m-p/8578830)
- Performance: an 18,000-curve DXF/SVG was "too large for one sketch"; advice is to split across layers/sketches because "Fusion's sketch solver is just not going to handle this much info in one sketch" — [Forum: Complex SVG/DXF Alternatives for Performance](https://forums.autodesk.com/t5/fusion-support-forum/complex-svg-dxf-alternatives-for-performance/td-p/12508894)
- CNC-plasma community complaints about Fusion's SVG handling — [Langmuir forum](https://forum.langmuirsystems.com/t/fusions-stupid-treatment-of-svg-files/20414)

**DXF import behavior (Insert > Insert DXF)**
- API `DXF2DImportOptions`: `isSingleSketchResult` (default false → one sketch per DXF layer; true merges all layers into one sketch); `isCreateControlPointSplines` (default false → splines "created as fixed splines that cannot be edited") — [DXF2DImportOptions Object](https://help.autodesk.com/cloudhelp/ENU/Fusion-360-API/files/DXF2DImportOptions.htm)
- Autodesk Support: if units are not specified when importing DXF, Fusion defaults to **centimetres**; fix via Sketch > Scale Sketch — [Forum: Importing DXF scale problems](https://forums.autodesk.com/t5/fusion-support/importing-dxf-scale-problems/td-p/7127906); [Forum: Importing DXF files](https://forums.autodesk.com/t5/fusion-design-validate-document/importing-dxf-files/m-p/6466117/highlight/true); DXF has no intrinsic units so a 2.54× error = inches read as cm, 25.4× = inches read as mm — [LightBurn forum](https://forum.lightburnsoftware.com/t/import-scaling-issue-from-fusion-360/5271)
- A user reported DXF splines linearized into many short segments ("instead of 20 or so curves you end up nearly 700") — [Forum: DXF Import Sketch Problem](https://forums.autodesk.com/t5/fusion-support/dxf-import-sketch-problem/td-p/10613289)
- Autodesk's DXF Import Utility add-in (Patrick Rainsberry) adds "Combine to a single sketch", arrangement into rows, closing sketch gaps, automatic extrusion and text import — [GitHub tapnair/DXFImporter](https://github.com/tapnair/DXFImporter); [Autodesk blog: How to Import DXF Files](https://www.autodesk.com/products/fusion-360/blog/how-to-import-dxf-files-to-fusion-360/)
- Fabricator guidance: Fusion's document default is centimetres; set Document Settings > Change Active Units to mm/in; exporting DXF from a sketch (right-click > Save As DXF) avoids unit changes that File > Export can introduce — [SendCutSend: change units](https://sendcutsend.com/faq/how-to-change-units-in-fusion-360/); [SendCutSend: export DXF from free Fusion](https://sendcutsend.com/faq/how-to-export-dxf-from-the-free-version-of-fusion/)
- Importing large DWG files is reported very slow — [Forum: importing DWG very very slow](https://forums.autodesk.com/t5/fusion-design-validate-document/importing-dwg-very-very-slow/m-p/6926732) **[older]**

### Inferences
- For the user's maze app (SVG with named layers): Fusion's SVG importer will flatten all layers/groups into one sketch, lose layer names, lose stroke widths (walls drawn as stroked centerlines become zero-width curves), and may mis-scale unless the SVG declares `width`/`height` in mm and uses a matching `viewBox`. Generating **DXF with one layer per maze layer** (boundary, walls, solution, dead-end-N) is the more faithful import path because Fusion maps DXF layers to separate sketches, which is what the user needs for CAM (profile vs pocket vs engrave).
- Wall thickness must be expressed as closed polygons (offset outlines) in the exported geometry, not as stroke width, for either SVG or DXF import into Fusion.
- Large mazes (thousands of segments) should be exported with arcs/lines rather than splines, and split across layers, to stay within the sketch solver's practical limits reported by users.

### Gaps
- No official Autodesk help page enumerating supported SVG elements (paths, polylines, arcs, transforms, `<use>`, nested groups) was surfaced; all SVG behavior above is forum-sourced (several threads are 2017–2022, so some may be stale).
- Whether Fusion honors SVG `transform` attributes and nested `<g>` transforms consistently was not documented in any source found.
- The exact current unit-default behavior of the Insert DXF dialog in the 2026 UI was not confirmed (reports conflict: "defaults to cm" vs "reads the DXF units").

## 4. Can a Fusion-native design (.f3d/.f3z) be generated externally without Fusion?

### Takeaway
No. `.f3d` is a proprietary, undocumented archive that Autodesk neither documents nor licenses for third-party writing; the only ways to produce one are inside Fusion (desktop or the cloud Automation API / Compute MCP). External tooling should generate STEP (3D), DXF (2D layered) or SVG (2D) for import.

### Cited Findings
- Fusion's main filetype `.f3d` "seems to be closed source and isn't supported by any other programs" — [Anson Biggs, How to export Fusion 360 files](https://notes.ansonbiggs.com/2018-09-12-how-to-export-fusion-360-files-to-other-file-types/) **[2018, but no contrary evidence found]**
- Autodesk's own format table lists `.f3d` only as a Fusion-authored format; every other CAD vendor appears as a translation input — [Supported file formats](https://help.autodesk.com/cloudhelp/ENU/Fusion-Import/files/TPD-SUPPORTED-FILE-FORMATS.htm)
- Model Derivative accepts `.f3d` as *input* and emits STEP/IGES/OBJ/STL/DWG/FBX/SVF — never `.f3d` as output — [Supported translations](https://aps.autodesk.com/en/docs/model-derivative/v2/supported-translations)
- The cloud Automation API runs Fusion itself in Autodesk's sandbox ("exposes more than 7,000 function endpoints"), which is the only sanctioned headless way to author Fusion-native content — [Fusion Automation API GA](https://aps.autodesk.com/blog/design-automation-api-fusion-now-generally-available)
- Fusion Compute MCP can create designs and export STL/STEP from the cloud without a local install — [Fusion Compute MCP: Public Beta](https://www.autodesk.com/products/fusion-360/blog/fusion-compute-mcp/)

### Inferences
- Any ".f3d writer" found in the wild would be reverse-engineered and unsupported; a Claude Code agent should never attempt to synthesize `.f3d` bytes. The correct architecture is: browser app → DXF/SVG/STEP → Fusion import (manual, add-in, or Automation API script), with the Fusion-native file created by Fusion.

### Gaps
- No Autodesk statement explicitly saying "the .f3d format is proprietary and may not be written by third parties" was found; the conclusion rests on the absence of any public specification or third-party writer across all sources searched.

## 5. Platform parity: Windows vs macOS for the API and CAM

### Takeaway
Fusion ships for Windows (10 22H2 / 11 22H2+) and macOS (14 Sonoma minimum, 15.7 recommended; Intel or Apple silicon) only — no Linux. The Python and TypeScript APIs and CAM are the same on both; C++ add-ins need per-OS builds (Visual Studio 2022 vs Xcode 16) and debugging differs; Windows-only extras (e.g. MFC UI) have no macOS equivalent.

### Cited Findings
- Windows: Windows 10 22H2 (build 19045+) or Windows 11 22H2 (build 22621+); minimum 2 performance cores/4 threads/3 GHz turbo; recommended 8+ performance cores, 32 GB+ RAM; the article notes Windows 10 22H2 reached Microsoft end-of-support 14 Oct 2025 — [System requirements for Autodesk Fusion](https://autodesk.com/de/support/technical/article/System-requirements-for-Autodesk-Fusion-360)
- macOS: minimum macOS 14 Sonoma (OpenCore Legacy Patcher unsupported), recommended macOS 15.7 Sequoia or newer; Intel Core i5 or Apple M1 minimum; 4 GB RAM min, 16 GB+ recommended — [Fusion product details](https://www.autodesk.com/products/fusion-360/product-details)
- C++: one `.cpp` with both `.vcxproj` and `.xcodeproj`; "the binary that's used by Fusion is OS specific"; "debugging your script or add-in is OS specific" — [C++ Specific Issues](https://help.autodesk.com/cloudhelp/ENU/Fusion-360-API/files/CPPSpecific_UM.htm); tutorial toolchain VS 2022 / Xcode 16 — [My First Fusion Plug-in Overview](https://blog.autodesk.io/my-first-fusion-plug-in-overview/); CMake lesson notes Windows/Mac paths differ and macOS adds a `lib` prefix — [Lesson 5: CMake](https://blog.autodesk.io/lesson-5-convert-it-to-a-cmake-project-c-optional-lesson/)
- MFC can be used in Windows add-ins (no macOS equivalent) — [Fusion Add-In with MFC](https://blog.autodesk.io/fusion-add-in-with-mfc/)
- Community reports that some C++ samples fail where Python equivalents work, and distributed C++ builds failed for ~half of colleagues — [Forum: Addin Development](https://forums.autodesk.com/t5/fusion-api-and-scripts-forum/addin-devlopment/m-p/12413379)
- Add-in/script default folders differ per OS (`%appdata%\Autodesk\...` vs `~/Library/Application Support/Autodesk/...`) — [ScriptSourceLocations](https://help.autodesk.com/cloudhelp/ENU/Fusion-360-API/files/ScriptSourceLocations.htm)

### Inferences
- For a Claude Code agent, Python (or TypeScript) add-ins are the portable choice; C++ should be avoided unless performance demands it.
- The lack of a Linux build means a cloud Linux container can never host Fusion; only the APS cloud APIs apply there.

### Gaps
- No source enumerated API features that exist only on one OS (beyond MFC); none were claimed to exist.
- CAM post-processor and toolpath parity across OSes was not explicitly stated in any source found (no reports of differences either).
