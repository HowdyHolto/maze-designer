## A1. rhino3dm: can an agent write a complete .3dm (layers, named objects, polylines, arcs, NURBS, planar surfaces, extrusions, meshes, user text) with no Rhino installed, on Linux and in a browser? Current version, gaps.

### Takeaway
Yes. rhino3dm 8.35.0 (Python on PyPI and JavaScript/WASM on npm, both released 2026-09-15) writes Rhino 8-format .3dm files headlessly on Linux x86_64/aarch64 and in the browser, including layers, object names, per-object user strings, polyline/arc/NURBS curves, planar surfaces, capped extrusions (solids), breps from primitives/surfaces, meshes and text dots; a local test wrote and re-read such a file with no Rhino present. It is a file/geometry *container* library: it has no booleans, no curve offset, no fillets, no planar-brep-from-curves, and no meshing of breps (those require Rhino or Rhino.Compute).

### Inferences
- For a maze (walls as rectangles/polylines, boundary as polygon, optional arcs for concentric mazes), rhino3dm is sufficient to emit a fully layered, named, mm-unit .3dm from Node, Python or directly from the browser app, because every needed primitive (polyline, arc, planar surface, capped extrusion for 3D walls, mesh) exists and was exercised locally. Wall solids can be produced as individual `Extrusion` objects per wall segment; what rhino3dm cannot do is union them into one solid or offset centerlines into wall outlines (the agent must compute offsets itself, which is trivial for axis-aligned rectangles).
- Because `Hatch` and `Text` classes exist in the JS typings but were not exercised, treat hatch/annotation authoring as "probably possible, unverified".
- The Python `ToByteArray`/`Notes`/document-user-text gaps are binding gaps, not file-format limits; writing to disk with `Write(path, 8)` is the reliable Python path, and per-object user strings (verified) are the practical place to tag metadata such as `role=profile-cut` or `depth=6mm`.

## A2. Open-source CAD kernels for producing STEP that Fusion and Rhino import: CadQuery, build123d, OCP/pythonOCC, FreeCAD headless — maturity, Linux install friction, capabilities, import fidelity

### Takeaway
CadQuery 2.8.0 (June 2026), build123d 0.13.0 (Sept 2026) and the OCP OpenCascade wheels (cadquery-ocp 8.0.1.1.0, Oct 2026, with manylinux_2_28 x86_64/aarch64 wheels) are all pip-installable on Linux with no GUI and produce true B-rep solids with booleans and fillets exported to STEP, which both Fusion and Rhino import as solids; FreeCAD's `FreeCADCmd` is a heavier alternative. STEP is a lossy exchange format only with respect to parametric history, sketches and constraints, not the solid geometry; the practical caveat is that STEP carries no 2D curve layers in a way Fusion will use, so STEP suits 3D wall solids rather than 2D toolpath outlines.

### Cited Findings
- cadquery 2.8.0 released 2026-06-21, `requires_python >= 3.11`, pure-Python wheel — [PyPI JSON](https://pypi.org/pypi/cadquery/json), [PyPI page](https://pypi.org/project/cadquery/)
- build123d 0.13.0 released 2026-09-21, `requires_python >=3.11,<3.15`, pure-Python wheel — [PyPI JSON](https://pypi.org/pypi/build123d/json), [PyPI page](https://pypi.org/project/build123d/)
- cadquery-ocp 8.0.1.1.0 (the OpenCascade binding both libraries use) released 2026-10-05 with wheels for manylinux_2_28_x86_64, manylinux_2_28_aarch64, macosx_11_0_arm64, macosx_11_0_x86_64 and win_amd64 — i.e. no conda needed on Linux — [PyPI JSON](https://pypi.org/pypi/cadquery-ocp/json), [PyPI page](https://pypi.org/project/cadquery-ocp/)

### Inferences
- For an agent in a Linux container, `pip install build123d` (or cadquery) now pulls prebuilt OCP wheels, so install friction is low; FreeCAD headless is viable but heavier (AppImage/conda) and adds nothing CadQuery/build123d lack for a maze.
- Using the OCC route, an agent can union all wall rectangles into one solid, fillet or chamfer edges, cut ball channels, and emit a single-body STEP; Fusion will open it as a body (no timeline), Rhino as a polysurface (possibly inside a block). This is the right path for 3D-printed or ball mazes; for 2D CNC/laser outlines, STEP is the wrong container because Fusion discards standalone curves.
- No direct CadQuery-STEP-into-Fusion fidelity benchmark was found; because both libraries write STEP via OpenCascade (also used by FreeCAD, whose STEP output is widely opened in Fusion), fidelity for simple prismatic solids is expected to be good, but this is inference.

### Gaps
- No source directly tested CadQuery/build123d STEP files opened in Fusion or Rhino 8 for face count, units or naming of bodies; the writer should recommend a one-off local test.
- Whether build123d/CadQuery STEP exports preserve body names/colors into Rhino layers or Fusion component names was not established.

## A3. 2D routes: ezdxf (DXF with layers) and SVG — how Rhino 8 imports SVG and DXF vs how Fusion imports SVG (into a sketch) and DXF (sketch import, layers); what is lost (layers, units, arcs vs polylines, closed regions)

### Takeaway
DXF is the more faithful 2D carrier into both programs: Rhino 8 preserves DXF layers, units, arcs and polylines (and even nests `$`-separated layer names in Rhino 9), and Fusion's Insert DXF lists the file's layers and can create one sketch per layer, with units selectable in the dialog. SVG is weaker in both: Rhino 8's SVG importer has options for groups and filled paths but has had scale bugs (viewBox vs width/height, RH-84096) and an arc-seam bug fixed only in 8 SR34; Fusion treats SVG units as pixels (needs a 3.779528x factor for 96-DPI files), imports geometry as fixed/locked sketch curves with splines that are hard to edit, flattens any layer structure into one sketch, and offers no SVG export. ezdxf 1.4.4 writes DXF R2018 with layers, LWPOLYLINE bulge arcs, ARC and SPLINE entities headlessly.

- Fusion DXF export: the cloud Export command converts DXF to centimetres, whereas right-click > Save As DXF on a sketch keeps sketch units — [Autodesk forum: Exporting DXF Scaling Issue](https://forums.autodesk.com/t5/fusion-support-forum/exporting-dxf-scaling-issue/td-p/9485539)
- A community Fusion add-in (tapnair/DXFImporter) exists for batch DXF import, and Autodesk's import blog notes multi-layer DXFs may extrude more reliably with "Combine to Single Sketch" and that the utility can close gaps — [tapnair/DXFImporter](https://github.com/tapnair/DXFImporter)
- Fusion's API `ImportManager` handles programmatic imports (DXF2D, STEP, etc.) — [Fusion API: ImportManager](https://help.autodesk.com/cloudhelp/ENU/Fusion-360-API/files/core_ImportManager.htm)

### Inferences
- For the user's maze app (SVG with layers `boundary`, `walls`, `solution`, `alt-path-N`, `dead-end-N`), the agent should add a DXF exporter (ezdxf server-side, or a small hand-rolled DXF writer in the browser, since DXF R12/R2000 ASCII is simple) with `$INSUNITS=4`, one DXF layer per SVG layer, LWPOLYLINE for straight walls and bulge arcs or ARC entities for concentric mazes. That single file imports into Rhino 8 with layers/units intact and into Fusion with one sketch per layer and selectable units — the two things SVG gets wrong in Fusion.
- If SVG is kept, write explicit `width="…mm" height="…mm"` plus a matching `viewBox` in mm, use absolute path commands, and avoid `transform` attributes; for Fusion, expect to apply a 3.779528 scale (96-DPI pixel assumption) or, better, use DXF.
- Arcs: Rhino keeps DXF ARC/bulge arcs as arcs; Fusion keeps DXF arcs as sketch arcs but linearizes splines, so avoid SPLINE entities for machinable geometry (use ARC/LWPOLYLINE). In SVG, both programs convert path arcs to native arcs in principle, but Rhino had the SR34 seam bug and Fusion has shown circle distortion, so DXF is the safer arc carrier.
- Closed regions: Fusion needs closed sketch profiles to pocket/extrude; Rhino needs closed planar curves for PlanarSrf/Extrude. Both are satisfied by closed LWPOLYLINEs; SVG `z`-closed paths generally work but Fusion's fixed/locked import makes gap repair tedious.

## B1. Fusion CAM: built-in capabilities, post processors, Personal Use restrictions in 2026, CAM API coverage, scripted post-processing

### Takeaway

## B3. For a maze cut as pockets (walls = pocket/engrave, boundary = profile), which end-to-end pipeline is simplest for an agent to automate: SVG/DXF → CAM directly, or via Rhino/Fusion?

### Takeaway
Direct SVG/DXF → CAM is the simplest and most automatable: the agent already produces layered 2D vectors, and Kiri:Moto, Carbide Create, Estlcam, Easel, VCarve and (for laser) LightBurn each turn those into G-code with a few clicks and no CAD step; Fusion adds parametric solids and the only *scriptable* CAM (via an add-in), while Rhino adds nothing to the CAM step unless RhinoCAM is bought. Generate DXF (not just SVG) to avoid unit/arc/layer losses.

## B4. Modeling-paradigm difference (Fusion: parametric, history-based solid CAD with timeline; Rhino: NURBS freeform with Grasshopper for parametrics) and its meaning for maze fabrication (wall-thickness changes, regeneration, ball-maze tolerances)

### Takeaway
Fusion is a history-based parametric solid modeler (change a dimension, the timeline replays), whereas Rhino is a direct NURBS/SubD/mesh modeler whose parametrics come from Grasshopper graphs; for a maze whose geometry is already generated algorithmically by the user's app, both paradigms are redundant for *topology* but differ in *re-fitting*: Fusion will regenerate pockets/toolpaths from an updated DXF only if the sketch is re-inserted (imported geometry is fixed, not dimension-driven), while a Grasshopper definition fed the maze's JSON could rebuild solids, offsets and tolerances live — but then still needs an external CAM.

### Cited Findings
- Autodesk forum answer: "Fusion 360 is a parametric modeler. You don't need any plugins to do parametric modeling" (contrasting Rhino needing Grasshopper) — [Autodesk forum: parametric modeling](https://forums.autodesk.com/t5/api-and-scripts/parametric-modeling/m-p/5454923)
- Rhino is "known for precise NURBS modeling, perfect for freeform designs"; it handles NURBS curves/surfaces/solids, SubD, point clouds and meshes; Grasshopper is Rhino's visual parametric layer used widely for parametric architecture; Fusion "shines with its all-in-one CAD, CAM, and CAE" — [vagon.io: Rhino 3D vs Fusion 360](https://vagon.io/blog/rhino-3d-vs-fusion-360), [Rhino supported file formats](https://www.rhino3d.com/features/file-formats/)
- A McNeel-forum practitioner: Fusion "is Extremely limited in terms of surfacing"; another said Grasshopper "seems to only be useful for paneling and patterns" (both opinions) — [McNeel Discourse: Help for new user](https://discourse.mcneel.com/t/help-for-new-user/77391?page=2)
- Fusion-imported SVG/DXF sketch geometry is "Fixed (green)" and imported splines cannot be edited like native ones; dimension-driven rescaling requires unfixing or the "Scale entire sketch at first dimension" preference — [Autodesk forum: working with SVG](https://forums.autodesk.com/t5/fusion-design-validate-document/working-with-svg/m-p/6847510), [Autodesk forum: Tip: Scaling SVG import](https://forums.autodesk.com/t5/fusion-design-validate-document/tip-scaling-svg-import-to-precise-dimensions/td-p/12012056)
- Fusion's API exposes design, sketch import (`Sketch.importSVG`, `ImportManager`) and CAM (setups, operations, `generateToolpath`, `NCProgram.postProcess`) in one scripting environment — [Fusion API: Sketch.importSVG](https://help.autodesk.com/cloudhelp/ENU/Fusion-360-API/files/fusion_Sketch_importSVG.htm), [Fusion API: CAM introduction](https://help.autodesk.com/cloudhelp/ENU/Fusion-360-API/files/CAMIntroduction_UM.htm)
- Grasshopper definitions can be solved headlessly via Rhino.Compute (Windows; Linux beta) — [Rhino.Compute FAQ](https://developer.rhino3d.com/guides/compute/compute-faq/)
- The maze app's own state already parameterizes `cellSize`, `wallFrac`, `toolDiamMm` and constraints `{minP, minW, minC}` with a tool-preset cascade, and regenerates doors by mm position on each `doGenerate()` — [project CLAUDE.md](/home/user/maze-designer/CLAUDE.md)

### Inferences
- Wall-thickness changes and regeneration already live in the maze app, so neither Fusion's timeline nor Grasshopper is needed to "re-parametrize" a maze; the agent should keep the app as the single source of truth and treat Fusion/Rhino as consumers of regenerated DXF/STEP. In Fusion this means re-inserting the DXF (or scripting the import) and letting dependent extrude/pocket features recompute where sketch profiles still resolve — robust if layer names and profile counts are stable, fragile if profile topology changes.
- Ball-maze tolerances (ball diameter + clearance, pocket depth, fillet at channel floor) are best expressed as parameters in the generator (channel width = ball Ø + 2×clearance; depth ≥ ball radius) and exported as closed channel polygons; if a 3D solid with floor fillets is wanted, OCC (build123d) can fillet headlessly, Fusion can fillet via API, and rhino3dm cannot (no fillet), so Rhino would need an in-app script.
- Where Rhino/Grasshopper pays off is visual exploration of concentric/polar or curved-wall mazes (NURBS arcs, SubD lids) and clean export to many formats; where Fusion pays off is integrated 2.5D CAM with simulation on the same model, scriptable in one Python add-in. Given the user's November/December renewal decision: the CAM step is the only place Fusion is irreplaceable without buying RhinoCAM, and free tools (Kiri:Moto, Carbide Create free/Pro, Estlcam) can fill that gap for 2.5D mazes.
