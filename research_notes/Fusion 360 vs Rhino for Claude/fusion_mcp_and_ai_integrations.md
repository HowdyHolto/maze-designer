# MCP servers and AI-agent integrations for Autodesk Fusion (state as of 11 Oct 2026)

Research notes. Scope: official Autodesk MCP servers, community Fusion MCP servers, bridge architecture/reliability, Claude Code vs Claude Desktop support, user reports, and non-MCP alternatives. Rhino/Grasshopper deliberately excluded.

Method/caveat: autodesk.com, help.autodesk.com, forums.autodesk.com, aps.autodesk.com, blog.autodesk.io, note.com, engineering.com, glama.ai, pulsemcp.com, smithery.ai and mcp.so were unreachable from this research environment (proxy denial). Facts about those pages come from search-engine summaries of them, or from GitHub/PyPI/anthropic.com/claude.com pages that were fetched directly. Where a fact rests only on a search summary, I say so. GitHub star counts and "pushed" (last commit) dates were pulled from the GitHub search API on 11 Oct 2026.

## Key question 1: Has Autodesk released an official MCP server / agent integration for Fusion (2025–2026)? Status, capabilities, access.

### Takeaway
Yes. Autodesk now ships three official Fusion MCP servers: (1) **Fusion MCP** — a local Streamable-HTTP server built into the Fusion desktop app (enable in Preferences > General > API; default endpoint `http://127.0.0.1:27182/mcp`), launched with Anthropic's "Claude for Creative Work" on 28 Apr 2026 and listed in Claude's connector directory since May 2026; (2) **Fusion Data MCP** — a remote/cloud server for hubs, projects, folders, items and metadata that does not need Fusion open; (3) **Fusion Compute MCP** (also called "Fusion Automation MCP" on one Autodesk page) — a cloud-hosted server in public beta since mid-September 2026 that runs headless Fusion sessions, exposes >7,000 TypeScript-API endpoints behind an `execute`-style tool, covers design, electronics, assembly, documents and manufacturing/CAM, and has been confirmed working with Claude Code. An APS "Workflow MCP" private beta was also announced at AU 2026.

**Fusion MCP (local) — how it works, how to enable**
- Autodesk MCP Server Help: enable via Fusion Preferences > General > API, check "Fusion MCP Server (runs locally on this device)"; Fusion then exposes `http://127.0.0.1:27182/mcp`; default port 27182; if the port is changed in preferences the client URL must match. The server "is local-only and needs no authentication" and "works with Streamable HTTP clients"; "the available tools are discovered by your MCP client at connection time and may change as capabilities evolve." (search summaries) — [Autodesk MCP Server Help: connecting](https://help.autodesk.com/view/ADSKMCP/ENU/?guid=ADSKMCP_FusionDesktopMcp_connecting_to_the_fusion_mcp_server_html); [Autodesk MCP Server Help: overview](https://help.autodesk.com/view/ADSKMCP/ENU/?guid=ADSKMCP_FusionDesktopMcp_autodesk_fusion_mcp_server_html)
- Claude connector directory entry "Autodesk Fusion" by Autodesk, Inc., "Anthropic verified", added May 2026: "Create, modify, and inspect CAD geometry in Fusion." Capabilities: sending commands to an active Fusion session, creating/modifying 3D geometry, sketches and features, creating primitives, applying modifications, querying design data. Requirements: Fusion installed and running locally; MCP server enabled under Preferences > General > API; Claude Desktop installed and configured with the correct port. Only Claude Desktop is mentioned; connection is local-only. — [claude.com marketplace](https://claude.com/marketplace/connectors/autodesk-fusion)
- Setup in Claude Desktop: Settings > Connectors, search "Fusion", pick the "Autodesk Fusion" tile (not the separate "Fusion Data MCP" tile); the connector already points at `http://127.0.0.1:27182/mcp`; tool permissions can be adjusted in the connector's configuration screen. (search summaries) — [Autodesk blog: Claude Desktop Connector](https://www.autodesk.com/products/fusion-360/blog/how-to-improve-your-fusion-workflow-with-the-claude-desktop-connector/); [Kanbara Tomonori, note.com](https://note.com/tomo1230ee/n/nac359cbe865c?hl=en)
- A local Fusion session must be open with a file active "because the MCP server modifies the session you're in, it doesn't spin one up." (search summary) — [Autodesk blog: Claude Desktop Connector](https://www.autodesk.com/products/fusion-360/blog/how-to-improve-your-fusion-workflow-with-the-claude-desktop-connector/)
- Autodesk's own guidance: the connector is "not ideal for creating complex production-ready CAD models from scratch" and "works best for structured automation"; start read-only (screenshots and data queries) before letting Claude change anything; save before any modification script ("the connector supports undo, but saving first is cheap insurance"). (search summaries) — [Autodesk blog: Claude Desktop Connector](https://www.autodesk.com/products/fusion-360/blog/how-to-improve-your-fusion-workflow-with-the-claude-desktop-connector/)
- Autodesk also published "Build Your Own Fusion Add-ins with the Fusion MCP" (using the MCP to help write add-ins; "the MCP supports undo workflows, but it's still good practice to save important files"). (search summary) — [Autodesk Fusion blog](https://www.autodesk.com/products/fusion-360/blog/build-your-own-fusion-add-ins-with-the-fusion-mcp/)

**Fusion MCP (local) — tools exposed (indirect evidence only)**
- Community wrapper fusion-cad-mcp sits in front of `127.0.0.1:27182/mcp` and says Fusion's built-in MCP "exposes four broad tools that take raw Python"; each wrapper tool "generates a Python script and runs it through Fusion's `execute`" tool. — [Mfrostbutter/fusion-cad-mcp](https://github.com/Mfrostbutter/fusion-cad-mcp)
- A Skool community post says "the Fusion MCP only exposes 3 tools, though those wrap the broader Fusion Python API" and that it is "shockingly good when using Claude Code with the Fusion 360 MCP". (search summary) — [AI Automation Society on Skool](https://www.skool.com/ai-automation-society/claude-and-fusion360-mcp-amazing-new-plugin-coming-soon)
- Autodesk's official **reference** implementation (AutodeskFusion360/FusionMCPSample, 23 stars, created 12 Dec 2025, updated 9 Oct 2026, MIT, "Reference implementation of an MCP server to run Fusion API scripts") exposes three tools: `execute_api_script` (runs Python with full Fusion API access), `get_screenshot` (viewport PNG, camera presets, 1–4096 px), `get_api_documentation` (searches Fusion API docs). It runs an HTTP server on `localhost:9100` with a `TaskManager` that marshals calls to Fusion's main thread via custom events; Cursor connects directly, "Claude requires the `mcp-remote` proxy run through `npx`, because Claude doesn't support local HTTP servers" (README written before Claude Desktop's HTTP connector support). Windows and macOS paths given. — [FusionMCPSample](https://github.com/AutodeskFusion360/FusionMCPSample); [FusionMCPSample add-in README](https://github.com/AutodeskFusion360/FusionMCPSample/blob/main/Fusion%20MCP%20Addin/README.md)
- The "pi" bridge to the official server registers Autodesk's tools "dynamically at connection time ... with a `fusion_` prefix" and gives examples: creating sketches, extruding, modifying features, "running command-based operations"; it adds its own `fusion_screenshot` and a confirmation gate for destructive scripts. — [porameht/pi-autodesk-fusion](https://github.com/porameht/pi-autodesk-fusion)
- A Codex plugin for Fusion Electronics "forwards Autodesk's existing tools unchanged" from `http://127.0.0.1:27182/mcp` and adds `fusion_mcp_electronics_list_commands`, `_start_command`, `_text_command`, `_export_eagle`, `_run_python`. — [mdlockyer/fusion-electronics](https://github.com/mdlockyer/fusion-electronics)
- Health check for the official server: `curl -s -o /dev/null -w "%{http_code}\n" http://127.0.0.1:27182/mcp` — 405 = healthy (POST-only route), 404 = server off, connection refused = Fusion not running. — [fusion-cad-mcp CONNECT.md](https://github.com/Mfrostbutter/fusion-cad-mcp/blob/main/CONNECT.md)

**Fusion Compute MCP / Fusion Automation MCP (cloud, public beta)**

(search summaries) — [Autodesk Fusion blog: Compute MCP public beta](https://www.autodesk.com/products/fusion-360/blog/fusion-compute-mcp/); [Autodesk feedback portal](https://feedback.autodesk.com/key/FusionAutomationMCP)

### Inferences
- The official local Fusion MCP is a thin "run Python/commands inside Fusion" server (3–4 broad tools), not a typed CAD toolkit; this matches the Autodesk reference sample (execute script / screenshot / API docs). Claude therefore does the CAD work by writing Fusion API Python on the fly — the quality of results depends on Claude's Fusion-API knowledge, not on a curated tool list.
- Status labels conflict (APS blog "tech preview" in April vs. a secondary report of "General Availability" in October). The safest reading is: local Fusion MCP and Fusion Data MCP are shipping and listed in Claude's directory; Compute MCP is public beta.
- For a paid Fusion subscriber, access is included: enable one checkbox in Fusion for the local server; the Compute MCP requires a Fusion Team hub plus the beta sign-up.
- Compute MCP is the only official path that exposes CAM (manufacturing) to an agent without the desktop app — relevant to the maze CAM goal.

### Gaps
- I could not fetch Autodesk's own help pages, so the exact names/descriptions of the official local server's 3–4 tools are not verified (sources disagree: "three tools" vs "four broad tools"). Verify by connecting a client and listing tools.
- No Autodesk source found that explicitly states macOS vs Windows support for the local Fusion MCP; the help text only says "runs locally on this device". All the forum problem reports I found were Windows; several community bridges and Japanese write-ups ran on macOS. Treat both OSes as supported pending confirmation.
- Exact tool list and the "seven tools" of Compute MCP not verified; pricing/consumption model for Compute MCP not found.
- Fusion Data MCP endpoint URL not found.

## Key question 2: Which community Fusion MCP servers exist (inventory with repo, author, stars, dates, license, tools, architecture, OS, install, clients, limitations)?

### Takeaway
About 45–50 community repos exist on GitHub; none has more than ~130 stars. The most useful in Oct 2026 are **faust-machines/fusion360-mcp-server** (117 stars, pushed 6 Oct 2026, MIT, 80–93 tools including CAM setup/operations/toolpaths/post-processing and STEP/STL/F3D export, Claude Code-tested), **Mfrostbutter/fusion-cad-mcp** (32 stars, 75 typed tools layered on Autodesk's official 27182 server, Claude Code + Desktop), **frankhommers/autodesk-fusion-mcp** (25 stars, in-process Streamable HTTP, zero dependencies, pushed 26 Sep 2026), and **mikan-atomoki/text-to-model** (64 tools incl. SVG/DXF import, Claude Code + Desktop). The once-popular **AuraFriday/Fusion-360-MCP-Server** (127 stars, proprietary licence, needs a separate "MCP-Link" server) has had no commits since 28 Jan 2026; **Joe-Spencer**, **ArchimedesCrypto**, **sockcymbal**, **mycelia1** and **jaskirat1616** are stale (no commits for 10–18 months). No Fusion server is in the official MCP registry.

## Key question 3: How do these servers bridge the gap (Fusion scripts must run inside the Fusion process)? Reliability/latency consequences; minimized Fusion; surviving Fusion updates.

### Takeaway
Every working bridge runs code inside Fusion's embedded Python add-in environment and marshals each request onto Fusion's UI/main thread via `adsk.core.CustomEvent` (the API is not thread-safe). Four patterns exist: (a) in-process HTTP/SSE server inside Fusion (Autodesk's official 27182 server, frankhommers, mikan-atomoki, Joe-Spencer, Autodesk's sample); (b) external stdio MCP process relaying to a localhost TCP/HTTP add-in (faust-machines, prim-design, ndoo, OSCAR, artapo, periscope); (c) file-polling via JSON files (Misterbra 0.5 s poll, rahayesj); (d) script generation only (ArchimedesCrypto). Consequences documented by the projects themselves: 30–120 s per-call timeouts, "one operation per call", hangs whenever a modal dialog is open or the main thread stalls, startup races when add-ins auto-load, port drift after updates, API drift between Fusion builds, and screenshots costing ~10k tokens. Nothing documents behaviour while Fusion is minimized.

### Cited Findings
- Main-thread constraint: "Fusion's Python API must only be called there [main thread]"; the add-in "uses Fusion's CustomEvent system to move HTTP requests onto the main thread". — [ndoo/fusion360-mcp-bridge](https://github.com/ndoo/fusion360-mcp-bridge); same design in [prim-design](https://github.com/prim-design/fusion-mcp), [faust-machines](https://github.com/faust-machines/fusion360-mcp-server), [frankhommers](https://github.com/frankhommers/autodesk-fusion-mcp), [OSCAR](https://github.com/Creative-Inertia/OSCAR_Public), [periscope](https://github.com/leonard-kmr/fusion360-mcp-periscope) ("the split exists because the Fusion API is not thread-safe"), and Autodesk's own sample `TaskManager` ("Runs Fusion API calls safely from background threads, using Fusion's custom event system"). — [FusionMCPSample](https://github.com/AutodeskFusion360/FusionMCPSample)
- Official server transport: Streamable HTTP, local-only, no auth, `http://127.0.0.1:27182/mcp`. (search summary) — [Autodesk MCP Server Help](https://help.autodesk.com/view/ADSKMCP/ENU/?guid=ADSKMCP_FusionDesktopMcp_connecting_to_the_fusion_mcp_server_html)
- Timeouts: faust-machines main-thread bridge 30 s, mutations never auto-retried; fozzfut 120 s for export/scripts, 30 s otherwise; rahayesj 45 s; tbrito88 recommends clients allow ~300 s per call and 60 s startup. — [faust-machines](https://github.com/faust-machines/fusion360-mcp-server); [fozzfut](https://github.com/fozzfut/FusionMCP); [rahayesj](https://github.com/rahayesj/ClaudeFusion360MCP); [tbrito88](https://github.com/tbrito88/fusion360-live-mcp)
- "One operation per tool call; batching crashes the add-in." — [faust-machines](https://github.com/faust-machines/fusion360-mcp-server)
- Startup race in an in-process server: when Fusion auto-loads the add-in at boot, "port 8765 accepts TCP connections (the kernel listen backlog does that)" but nothing serves requests because `run()` bound the port "before Fusion's main-thread event loop is pumping"; and main-thread dispatch had no timeout so "any main-thread stall turns into a permanent client hang instead of a fast failure". Fix (PR opened 22 Aug, merged 7 Sep 2026): defer binding until a `__startup_ping__` round-trips through the CustomEvent dispatcher; add `MCP_MAIN_THREAD_TIMEOUT` (default 120 s). — [frankhommers PR #3](https://github.com/frankhommers/autodesk-fusion-mcp/pull/3)
- Modal dialogs block the bridge: periscope returns `fusion_busy` when "a modal dialog or long compute" is active; a CNC programmer reports that with the official connector, while a Fusion command dialog is open screenshots are blocked and "Claude goes completely blind at the most critical step — geometry selection". — [periscope](https://github.com/leonard-kmr/fusion360-mcp-periscope); [Autodesk Community](https://forums.autodesk.com/t5/fusion-api-and-scripts-forum/fusion-mcp-feedback-dialog-visibility-limitation-with-claude/td-p/14120453)
- Official-server connection failures reported on the Autodesk forum: Windows 11 user — server on 27182 "returns malformed HTTP response, Claude can't connect"; another Windows/Claude Desktop user — server connects, receives `initialize`, then drops with transport-closed, root cause "Fusion was picking a fresh ephemeral port on every launch rather than honoring 27182". (search summaries) — [Autodesk Community: malformed HTTP](https://forums.autodesk.com/t5/fusion-support-forum/fusion-mcp-server-127-0-0-1-27182-returns-malformed-http/td-p/14292201); [Autodesk Community: disconnects after initialize](https://forums.autodesk.com/t5/fusion-api-and-scripts-forum/fusion-mcp-server-disconnects-immediately-after-initialize/td-p/14139904)
- After Fusion is closed/restarted the client session goes stale; fusion-cad-mcp "re-handshakes on a rejected session" but "no tool call can fix a stale client session from the inside" — reconnect via `/mcp` in Claude Code. — [fusion-cad-mcp CONNECT.md](https://github.com/Mfrostbutter/fusion-cad-mcp/blob/main/CONNECT.md)
- A setup guide advises, after a Fusion update, to "check that the MCP checkbox and port are visible in API settings". (search summary) — [TechDraw AI](https://techdrawai.com/blog/connect-claude-to-fusion-360)
- API drift across Fusion builds: `TimelineObject.deleteObject` is missing before ~2705 so the bridge falls back to `entity.deleteMe()`; some faust-machines tools "need a 2026 or later Fusion build"; tbrito88 had to fix the faust-machines server to work on Fusion 2704.1.53. — [ArnaudUnreal/fusion360-mcp](https://github.com/ArnaudUnreal/fusion360-mcp); [faust-machines](https://github.com/faust-machines/fusion360-mcp-server); [tbrito88](https://github.com/tbrito88/fusion360-live-mcp)

- Screenshot cost: `screenshot()` is "costly at about 10k tokens". — [ArnaudUnreal/fusion360-mcp](https://github.com/ArnaudUnreal/fusion360-mcp)
- Security posture: official server has no auth (local-only); faust-machines socket "has no authentication, so it should only run on a trusted LAN"; ndoo/OSCAR/artapo/periscope use bearer tokens; AuraFriday notes "Python execution has full system access"; a reviewer warns frankhommers' add-in "runs any Python the AI sends without a confirmation step". — [faust-machines](https://github.com/faust-machines/fusion360-mcp-server); [AuraFriday](https://github.com/AuraFriday/Fusion-360-MCP-Server); [greenlitbooks field note](https://greenlitbooks.com/field-notes/is-autodesk-fusion-mcp-safe)

- Cloud alternative removes the desktop entirely: Compute MCP runs Fusion sessions in Autodesk's cloud (1 h max, 15 min idle, 2 concurrent). — [Autodesk Fusion blog: Compute MCP](https://www.autodesk.com/products/fusion-360/blog/fusion-compute-mcp/)

### Inferences
- Latency is dominated by Fusion's main-thread execution, not by the MCP hop; a design with many small tool calls (e.g., drawing a maze wall by wall) will be slow and fragile ("one op per call", 30 s timeouts). Generating the whole maze as one Python script and executing it in a single `execute` call is the robust pattern — and fits the official server's design.
- Because the official server is compiled into Fusion, it survives Fusion's frequent auto-updates by construction (Autodesk ships it), although the forum reports suggest re-checking the preferences checkbox/port after updates. Community add-ins live in the user's AddIns folder (not the versioned install), so they persist across updates, but their Python can break when the API changes between builds (documented above). This is an inference from the install paths; no source tested it explicitly.
- Modal dialogs, "busy" states and the active-document requirement mean the bridge is only reliable when Fusion is sitting idle in the Design workspace with a document open and no command dialog active.

### Gaps
- No source addresses whether any bridge works while Fusion is minimized or in the background (likely fine for API calls since the server thread keeps running, but viewport screenshots may be blank — unverified).
- No measured latency numbers for the official server; only the Compute MCP demo's "about 6.5 seconds" for CAM toolpath generation.

## Key question 6: Non-MCP agent approaches people use with Fusion + Claude (scripts, CadQuery/build123d → STEP, computer use)?

### Takeaway
Three alternatives are in active use: (1) Claude writes Fusion API Python scripts that the user pastes into Fusion's Scripts and Add-Ins dialog (the original, still-common workflow; also what script-generation "MCP" servers like ArchimedesCrypto/mycelia1 do); (2) code-CAD kernels outside Fusion — build123d/CadQuery via MCP servers (pzfreo/build123d-mcp, Casys-AI/mcp-build123d) that export STEP (B-rep preserved, body names kept) for import into Fusion; (3) Claude "computer use" driving the Fusion UI via screenshots/clicks. Skill-based layers (Chocksy/fusion-agent-kit, fusion-mcpilot, rahayesj's SKILL.md) turn the MCP `execute` hatch back into "re-runnable build scripts", which is effectively approach (1) automated.

### Cited Findings
- Script-writing workflow: "Claude has deep knowledge of the Fusion 360 API and Python, so you can describe a part or feature in plain English and Claude will generate the script to create it. Claude can iterate, modifying the script when the geometry comes out wrong." ### Inferences
- For the maze use case specifically, the lowest-risk pipeline is: the browser app (or Claude Code) emits geometry as SVG/DXF **or** as a self-contained Fusion Python script; Claude Code sends that script in one `execute` call to the official local Fusion MCP (or a wrapper like fusion-cad-mcp), which creates the sketch, extrudes walls/floor, and exports STEP/STL/DXF; CAM is then either scripted via `adsk.cam` in the same execute call, driven through faust-machines' CAM tools, or handed to Autodesk's cloud Compute MCP. Everything in that chain exists today, but no source demonstrates it end to end for mazes.
- The build123d/CadQuery → STEP route avoids Fusion's main-thread fragility entirely and is scriptable in a cloud Claude Code session, at the cost of losing Fusion's parametric timeline (imported STEP is a dumb solid) and needing a separate CAM step in Fusion.
