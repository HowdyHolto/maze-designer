# Keep Rhino 8, Let Fusion Lapse

**Keep Rhino 8 + Grasshopper and let the commercial Fusion subscription expire in November/December 2026** — but if you still qualify (non-commercial, under US$1,000/year from maze sales), downgrade to the free *Fusion for Personal Use* rather than uninstalling, so you keep 2.5-axis CAM and STEP export as a fallback. Rhino wins the Claude Code interoperability test on every axis that matters to a terminal agent: McNeel's **rhino3dm** library (MIT, `pip`/`npm`, v8.35.0 released 15 Sep 2026) let Claude Code write a native, layered Rhino 8 `.3dm` from this session's Linux container with no Rhino installed — a result verified here, not read on a web page — whereas Fusion's `.f3d` cannot be written by anything except Fusion itself; Rhino 8 ships a `rhinocode` command-line tool on both Windows and macOS while Fusion has no CLI and no headless desktop mode; McNeel's official MCP server is free, MIT-licensed and documents Claude Code by name, while Autodesk's official Fusion MCP is "for Fusion subscribers" at **US$680/year**; Rhino 8 imports *and* exports SVG, DXF, STEP, STL, 3MF, AI and PDF natively, while Fusion's SVG import is lossy and `.3dm` import is a paid-tier-only feature; and on Windows your existing licence also unlocks a free local **Rhino.Compute** REST server. What you give up is real but narrow: Fusion's integrated, API-scriptable CAM (the only scriptable CAM in this comparison), its parametric timeline, and Autodesk's beta cloud **Fusion Compute MCP** — the one route that lets a Claude Code session in a Linux container run CAD *and* CAM with no desktop at all. For a 2.5D pocketed maze, those losses are covered by free or sub-$120 CAM tools (Kiri:Moto, Carbide Create Pro, Estlcam, LightBurn) that consume the DXF/SVG your app already produces. The single highest-value engineering step is to add a **DXF exporter** (one layer per maze layer, millimetre units) and, via `rhino3dm.js`, a **`.3dm` exporter** to `index.html`; the start-today checklist is in the final section.

Vendor-page facts below were therefore obtained from search-engine extracts of the cited pages; McNeel's developer guides and RhinoAI docs were read from their public GitHub source repositories; PyPI, npm and GitHub were read directly. Anything marked "verified" was executed in this session's Linux container (recorded in `coordinator_empirical_checks.md`). Treat vendor-page wording as paraphrase and spot-check anything you will spend money on.*

## rhino3dm and `rhinocode` give Claude Code a headless path that Fusion structurally cannot offer

The decisive technical fact is that **Rhino's file format is open and Fusion's is not**. McNeel publishes rhino3dm, an MIT-licensed wrapper around openNURBS with a RhinoCommon-style API for Python, JavaScript/WebAssembly and .NET; version **8.35.0 shipped to PyPI and npm on 15 Sep 2026** with wheels for CPython 3.9–3.14 on Windows x64/ARM64, macOS universal2 and manylinux x86_64/aarch64 ([PyPI](https://pypi.org/project/rhino3dm/); [npm](https://www.npmjs.com/package/rhino3dm); [GitHub](https://github.com/mcneel/rhino3dm)). The coordinator tested this directly in the Linux container: `pip install rhino3dm` succeeded, a script created a `File3dm` with `ModelUnitSystem = Millimeters`, three named, coloured layers (`boundary`, `walls`, `solution`), a closed 100×80 mm boundary polyline, four named wall `LineCurve`s, an `Arc` on the solution layer and a capped 10 mm `Extrusion`; `File3dm.Write("maze_test.3dm", 8)` returned `True`, produced a **10,049-byte Rhino 8 file**, and read-back recovered all 7 objects with layer indices and object names intact. The whole install-plus-write took under a minute and the venv footprint was a few megabytes. A second researcher's local test extended this to `PlaneSurface`, `Brep.CreateFromBox`, a quad `Mesh`, a `TextDot`, and per-object user strings (`SetUserString("role","profile-cut")`), all of which round-tripped ([PyPI](https://pypi.org/project/rhino3dm/)). The npm tarball bundles `rhino3dm.wasm` and TypeScript typings exposing `File3dm.toByteArray()`, `File3dmLayerTable.addLayer(name, color)` and `Extrusion.create(planarCurve, height, cap)`, which means **your single-file browser maze app can build a `.3dm` in memory and hand the user a download** without any server ([npm tarball](https://registry.npmjs.org/rhino3dm/-/rhino3dm-8.35.0.tgz)).

rhino3dm's limits are equally clear and equally verified: a grep of the typings found no `boolean`, `offset(`, `fillet`, `loft`, `sweep`, `split(` or `trim(` methods, and the Python `Brep` class exposes only primitive constructors (`CreateFromBox`, `CreateFromCylinder`, `CreateFromSurface`, …) with no `CreateBoolean*` or `CreatePlanarBreps`. McNeel's own description of Rhino.Compute confirms this is by design — Compute "adds functions missing from openNURBS, including closest point, intersection, meshing, interpolation, booleans, and area/mass properties" ([Rhino.Compute features](https://developer.rhino3d.com/guides/compute/features/)). For a maze this matters less than it sounds: axis-aligned wall rectangles can be offset arithmetically in your own code, and each wall can be emitted as its own capped `Extrusion`; only unioning them into one solid, filleting channel floors, or meshing a Brep needs Rhino itself.

When Rhino *is* available, it is far more terminal-friendly than Fusion. Rhino 8 (≥ 8.11) ships a **`rhinocode` CLI** on Windows (`%PROGRAMFILES%\Rhino 8\System`) and macOS (`/Applications/Rhino 8.app/Contents/Resources/bin`) that lists running Rhino instances (`rhinocode list --json`), sends command strings (`rhinocode command "_circle 0 0 0 20"`) and runs `.py`/`.cs` script files against an instance in which `StartScriptServer` has been run; `rhinocode project build` compiles `.rhp`/`.gha`/`.yak` packages and "doesn't require a running Rhino instance, so it works in CI/CD pipelines" ([RhinoCode CLI guide](https://developer.rhino3d.com/guides/scripting/advanced-cli/)). Rhino can also be launched from a shell with a script and told to exit — `Rhino.exe /runscript="-cmd1 -cmd2 _-Exit" file.3dm` on Windows, `open "/Applications/Rhino 8.app" --args -nosplash -runscript "…"` on macOS — and the `_-ScriptEditor _R "path.py"` macro runs a Python 3 or C# file non-interactively, while `-GrasshopperPlayer <file.gh>` solves a definition with no Grasshopper window ([Running Rhino from the command line](https://developer.rhino3d.com/guides/cpp/running-rhino-from-command-line/); [Mac startup flags](https://docs.mcneel.com/rhino/8mac/help/en-us/information/startingrhino.htm); [ScriptEditor macros](https://developer.rhino3d.com/guides/scripting/advanced-scripteditor-macros/); [Grasshopper commands](https://docs.mcneel.com/rhino/8/help/en-us/commands/grasshopper.htm)). Inside Rhino, the unified ScriptEditor runs **CPython 3.9** (`~/.rhinocode/py39-rh8`), IronPython 2.7 and modern C# on Windows and Mac, and Python 3 scripts declare pip dependencies inline (`#r: numpy`, `#requirements: ezdxf, shapely`, PEP 723 blocks) which Rhino installs itself ([Packages & Libraries guide](https://developer.rhino3d.com/guides/scripting/advanced-packages/); [Language initialization](https://developer.rhino3d.com/guides/scripting/advanced-langinit/)). One caution: CPython 3.9 reached upstream end-of-life in October 2025, so newer wheels may stop publishing cp39 builds — pin versions in `#r:` lines.

Windows users get two more layers. **Rhino.Compute** wraps a headless Rhino behind a REST API (`http://localhost:6500`, "2400+ RhinoCommon API calls" plus Grasshopper-definition solving) and on a desktop PC "checks for a standard Rhino licence at startup" with no extra cost; on any Windows Server or Linux/cloud VM it needs Core-Hour Billing at **US$0.10 per core per hour of uptime**, and macOS "is not supported" ([Compute FAQ](https://developer.rhino3d.com/guides/compute/compute-faq/); [Core-Hour Billing](https://developer.rhino3d.com/guides/compute/core-hour-billing/); [Compute development](https://developer.rhino3d.com/guides/compute/development/)). A Linux build exists but McNeel calls it "WIP software … not for production", and it supports "only 3dm files" for import/export ([Compute on Linux](https://developer.rhino3d.com/guides/compute/compute-linux-getting-started/)). The `rhinoinside` pip package (0.8.2, June 2025; Windows only) goes further: `import rhinoinside; rhinoinside.load(8, 'net8.0'); import Rhino` puts the full RhinoCommon geometry kernel inside Claude Code's own CPython process ([PyPI rhinoinside](https://pypi.org/project/rhinoinside/)).

Fusion's story is the mirror image. Its desktop API runs **only inside a live, logged-in GUI session**; Autodesk's forum answer to "can I run a Python file that models in Fusion from the command line" is that this "will need further development" — i.e. Fusion must be open ([Autodesk forum](https://forums.autodesk.com/t5/fusion-api-and-scripts-forum/is-it-possible-to-execute-a-command-from-the-command-line-that/m-p/12265338); [Fusion360 headless thread](https://forums.autodesk.com/t5/fusion-api-and-scripts-forum/fusion360-headless/m-p/12063439)). The embedded interpreter is Python 3.12 moving to 3.14 "in the January release", there is no pip integration (packages are vendored into the add-in's `./lib` folder), and every external trigger — community bridges and Autodesk's own MCP alike — is an add-in that opens a localhost socket and marshals each call onto Fusion's main thread via `CustomEvent` ([Autodesk developer blog](https://blog.autodesk.io/fusion-python-upgrade-and-more/); [FusionMCPSample](https://github.com/AutodeskFusion360/FusionMCPSample)). Autodesk's headless answer is in the cloud: the **Fusion Automation API** (GA 19 May 2025) runs TypeScript scripts in a sandbox and bills Premium API use at **3.0 Flex tokens per processing hour** — roughly US$9/hour at the ~$3/token list rate, metered to the second including file transfer — with PAT authentication deprecated on 29 Jul 2026 in favour of two- plus three-legged OAuth ([Automation API GA](https://aps.autodesk.com/blog/design-automation-api-fusion-now-generally-available); [product page](https://aps.autodesk.com/apis-and-services/fusion-automation-api); [PAT deprecation](https://aps.autodesk.com/node/4020)). And `.f3d` is a closed format: Autodesk's Model Derivative service accepts `.f3d` as *input* and emits STEP/IGES/OBJ/STL/DWG, never the reverse, and no third-party writer exists ([supported translations](https://aps.autodesk.com/en/docs/model-derivative/v2/supported-translations)). The coordinator's second test shows the practical consequence: `pip install build123d` did produce a valid 28,938-byte STEP solid for Fusion import, but the OpenCascade wheel pushed the venv to **~1.0 GB** (versus a few MB for rhino3dm), and the output is a generic dumb solid, not a Fusion-native parametric design — and Rhino opens the same STEP, so that path is neutral between the two programs.

## Both vendors now ship official MCP servers, but only McNeel's is free, MIT and documented for Claude Code

2026 changed the agent calculus for both products. Autodesk launched a local **Fusion MCP** with Anthropic's "Claude for Creative Work" on 28 Apr 2026: enable "Fusion MCP Server (runs locally on this device)" under Preferences > General > API and Fusion serves Streamable HTTP at **`http://127.0.0.1:27182/mcp`**, local-only with no authentication, tools "discovered by your MCP client at connection time" ([Anthropic announcement](https://www.anthropic.com/news/claude-for-creative-work); [Autodesk MCP help](https://help.autodesk.com/view/ADSKMCP/ENU/?guid=ADSKMCP_FusionDesktopMcp_connecting_to_the_fusion_mcp_server_html)). The server is thin — community wrappers report it "exposes four broad tools that take raw Python", mirroring Autodesk's reference sample (`execute_api_script`, `get_screenshot`, `get_api_documentation`) — so Claude does the CAD by writing Fusion API Python on the fly ([fusion-cad-mcp](https://github.com/Mfrostbutter/fusion-cad-mcp); [FusionMCPSample](https://github.com/AutodeskFusion360/FusionMCPSample)). Autodesk also ships a remote **Fusion Data MCP** (hubs, folders, permissions; no Fusion open) and, since mid-September 2026, the cloud **Fusion Compute MCP** in public beta: headless Fusion sessions exposing "more than 7,000 endpoints behind a single execute tool", covering design, assembly, documents and manufacturing/CAM, limited to **two concurrent sessions per user, one hour maximum, 15 minutes idle**, requiring an Autodesk account, an active Fusion licence and a Fusion Team hub at `https://developer.api.autodesk.com/da/v3/mcp/fusion` ([Fusion Data MCP](https://www.autodesk.com/products/fusion-360/blog/introducing-the-autodesk-fusion-data-mcp-server/); [Compute MCP beta](https://www.autodesk.com/products/fusion-360/blog/fusion-compute-mcp/)). A forum thread confirms "VS Code, Claude.ai, Claude Code, or Google Antigravity are the confirmed-working clients" for Compute MCP while Codex is rejected with `AUTH-001` ([Autodesk forum](https://forums.autodesk.com/t5/fusion-api-and-scripts-forum/fusion-compute-mcp-rejects-openai-codex-cimd-with-auth-001-while/td-p/14270344)). The catch for your decision: Autodesk words the connector as being "for Fusion subscribers", All3DP noted "it's not clear if the free subscription qualifies", and no researcher found any Autodesk statement that Personal Use accounts get the MCP servers ([Fusion comes to Claude](https://www.autodesk.com/products/fusion-360/blog/fusion-comes-to-claude-for-creative-work-bringing-ai-directly-into-the-design-workflow/); [All3DP](https://all3dp.com/4/claude-comes-to-cad-anthropics-ai-can-now-help-build-3d-models-in-autodesk-fusion/)). Autodesk's own usage guidance is also sober: the connector is "not ideal for creating complex production-ready CAD models from scratch", "works best for structured automation", and you should "start read-only" and save before any modification ([Claude Desktop connector guide](https://www.autodesk.com/products/fusion-360/blog/how-to-improve-your-fusion-workflow-with-the-claude-desktop-connector/)).

McNeel's answer is the **Rhino MCP Platform** in the `mcneel/RhinoAI` repository: MIT-licensed ("Copyright (c) 2026 Robert McNeel & Associates"), 358 stars, last commit 6 Oct 2026, installed in Rhino 8 as the Yak package **`Rhino-MCP-Platform`** via `PackageManager`, connected with the **`MCPConnect`** command, and documented for "Claude Desktop, Claude Code, GitHub Copilot, OpenAI Codex, Gemini CLI, or a local model" ([RhinoAI README](https://raw.githubusercontent.com/mcneel/rhinoai/rhino-9.x/README.md); [GitHub](https://github.com/mcneel/RhinoAI)). The Claude Code page is explicit: install the plugin, "run `MCPConnect` in Rhino, paste the prompt it gives into a new Claude Code session, and restart Claude Code if prompted" ([cc-plugin.md](https://raw.githubusercontent.com/mcneel/rhinoai/rhino-9.x/docs/content/docs/getting-started/cc-plugin.md)). Architecturally the Rhino plugin hosts an in-process HTTP MCP endpoint and a stdio-to-HTTP **router** that "emits 38 tool proxies"; the tool surface includes `run_python`, `run_command`, `get_viewport_image`, document slots (`spawn_slot`, `open_doc`, `list_slots` — letting an agent start and drive several Rhino instances in parallel), and Grasshopper graph tools for GH1 on Rhino 8 (`g1_apply_graph`, `g1_solve_graph`) and GH2 on the Rhino 9 Beta ([PLAN.md](https://raw.githubusercontent.com/mcneel/rhinoai/main/PLAN.md); [headless render farm doc](https://raw.githubusercontent.com/mcneel/rhinoai/rhino-9.x/docs/content/docs/advanced/headless-render-farm.md); [releases](https://github.com/mcneel/rhinoai/releases)). McNeel announced it as an official Rhino BETA feature on 30 Sep 2026 — "RhinoAI is a plugin that connects Rhino and Grasshopper (1 & 2) to AI assistants like Claude, GitHub Copilot, Codex, Gemini, and Local LLMs" — with an in-Rhino **AI Panel** (`AIPanel` command) that is default in the Rhino 9 Beta and installable in Rhino 8 ([McNeel forum announcement](https://discourse.mcneel.com/t/rhino-beta-feature-rhinoai/223146)). Plugin 0.3.0 (30 Sep 2026) was rewritten "from Python to C#" and lowered the minimum Rhino build to **8.19** ([releases](https://github.com/mcneel/rhinoai/releases)). Rough edges exist and are documented by McNeel itself: the troubleshooting page states "**Intel Macs are not supported**" (the router ships only for Apple Silicon), the router "defaults to Rhino 8" (add `"args": ["-v", "9"]` in `~/.claude.json` for the Beta), and forum users reported the server initially answered on port 10500 via `MCPStart`, failed with Claude Desktop's Connectors UI, and was later "moved off the default port 10500" — so always use the URL `MCPConnect` prints rather than one from a blog ([troubleshooting.md](https://raw.githubusercontent.com/mcneel/rhinoai/rhino-9.x/docs/content/docs/troubleshooting.md); [Rhino MCP Server thread](https://discourse.mcneel.com/t/rhino-mcp-server/216568)).

The community ecosystems differ in maturity. On the Rhino side one project dominates: **jingcheng-chen/rhinomcp** (MIT, ~1.1k stars, v0.4.1.1 on 14 Sep 2026) — a Python MCP server on the official SDK 2.x talking TCP to a C# RhinoCommon plugin on `127.0.0.1:1999`, installed via Package Manager (`rhinomcp`), started with `mcpstart`, and registered in one line: **`claude mcp add rhino -- uvx rhinomcp@latest`**; it targets "Rhino 8 on Windows and macOS" and offers typed geometry tools (booleans, loft, sweep1, `offset_curve`, `extrude_curve`, layers, attributes), `execute_rhinoscript_python_code`, `execute_rhinocommon_csharp_code`, viewport capture, undo/redo and a `gh_*` Grasshopper suite ([GitHub](https://github.com/jingcheng-chen/rhinomcp); [releases](https://github.com/jingcheng-chen/rhinomcp/releases)). For Grasshopper specifically, **Cordyceps** (105 stars, v1.5.0 on 29 Aug 2026) is a `.gha` that serves Streamable HTTP at `http://127.0.0.1:26929/mcp` — Claude Code connects with `claude mcp add --transport http` — on Rhino 8.21+ for Windows and macOS, with a `gh_script` tool for configuring Script components ([GitHub](https://github.com/brookstalley/cordyceps)); ETH Zurich's **LAMCP** (`claude mcp add lamcp --scope user -- uvx lamcp`) specialises in Python script components with hot reload ([GitHub](https://github.com/gramaziokohler/lamcp)). **EaseHee/rhino-mcp** is notable for a "standalone mode" that wraps rhino3dm so it "works without Rhino installed", plus Streamable HTTP/Docker transports documented for the claude.ai remote connector via a tunnel ([GitHub](https://github.com/easehee/rhino-mcp)). The **Food4Rhino** marketplace you asked about mostly re-lists these: `rhinomcp` by `ccc159` *is* jingcheng-chen's project (1,496 downloads, listing version 0.2.1 dated March 2026 — well behind GitHub's 0.4.1.1); **RhinoAiMCP** by "RhinoPort" is the most downloaded (~31,000), free as a V1 beta but requiring a purchased licence key for V2, Rhino 7 and 8, Windows and Mac, with "Claude Opus and Sonnet as best-tested models" and no price located; **RhinoAI-GrasshopperAI-RhinoMCP** by "Yantan" is free, Rhino 8, Windows-only, and generates RhinoCommon C# from prompts; **Almond MCP** adds a semantic design layer with Karamba3D structural checks ([Food4Rhino rhinomcp](https://www.food4rhino.com/en/app/rhinomcp); [RhinoAiMCP](https://www.food4rhino.com/en/app/rhinoaimcp); [Yantan](https://www.food4rhino.com/en/app/rhinoai-grasshopperai-rhinomcp); [Almond MCP](https://www.food4rhino.com/en/app/almond-mcp)). Because food4rhino.com was unreachable, these are search-summary facts; the practical advice is that **McNeel's official plugin is distributed through the in-Rhino Package Manager, not Food4Rhino**, and the Package Manager copies of `rhinomcp` and `Cordyceps` are fresher than their Food4Rhino listings.

On the Fusion side roughly 45–50 community repositories exist, none above ~130 stars, and no Fusion server appears in the official MCP registry ([MCP registry search](https://registry.modelcontextprotocol.io/v0/servers?search=fusion&limit=50)). The useful ones in October 2026 are **faust-machines/fusion360-mcp-server** (117 stars, pushed 6 Oct 2026, MIT; 80–93 tools including CAM setup/operations/toolpaths/post-processing, STEP/STL/F3D export, Claude Code-tested via `claude mcp add fusion360 -- uvx fusion360-mcp-server --mode socket` against an add-in on TCP 9876), **Mfrostbutter/fusion-cad-mcp** (75 typed tools layered on Autodesk's official 27182 server — no add-in to install — `claude mcp add fusion -- fusion-cad-mcp`), **frankhommers/autodesk-fusion-mcp** (in-process Streamable HTTP on `127.0.0.1:8765/mcp`, zero dependencies) and **mikan-atomoki/text-to-model** (64 tools, the only one with explicit `import_svg`/`import_dxf` tools) ([faust-machines](https://github.com/faust-machines/fusion360-mcp-server); [fusion-cad-mcp CONNECT.md](https://github.com/Mfrostbutter/fusion-cad-mcp/blob/main/CONNECT.md); [frankhommers](https://github.com/frankhommers/autodesk-fusion-mcp); [text-to-model](https://github.com/mikan-atomoki/text-to-model)). The once-popular AuraFriday server (127 stars) is proprietary and has had no commits since 28 Jan 2026 ([GitHub](https://github.com/AuraFriday/Fusion-360-MCP-Server)). Reliability reports cluster around Fusion's main-thread constraint: faust-machines warns "one operation per tool call; batching crashes the add-in" with a 30 s bridge timeout; Autodesk forum users hit a "malformed HTTP response" on 27182 and a disconnect caused by "Fusion picking a fresh ephemeral port on every launch rather than honoring 27182"; and a CNC programmer found that while a Fusion command dialog is open "Claude goes completely blind at the most critical step — geometry selection" ([faust-machines](https://github.com/faust-machines/fusion360-mcp-server); [ephemeral-port thread](https://forums.autodesk.com/t5/fusion-api-and-scripts-forum/fusion-mcp-server-disconnects-immediately-after-initialize/td-p/14139904); [dialog-visibility thread](https://forums.autodesk.com/t5/fusion-api-and-scripts-forum/fusion-mcp-feedback-dialog-visibility-limitation-with-claude/td-p/14120453)).

User experience reports converge across both ecosystems on the same lesson, which happens to suit a maze perfectly: **Claude is reliable at scripted, code-defined geometry and expensive at conversational, object-by-object modelling.** A Rhino user let Claude build a car through the official server for 35 minutes and "ran out of Claude credits before finishing"; another "chewed through half my daily token quota on Claude Pro in one conversation"; yet a blogger built "100 Rhino models almost on autopilot" with rhinomcp and Claude Code in "a few hours" of active time ([first-try thread](https://discourse.mcneel.com/t/rhino-mcp-claude-first-try/223183); [Rhino MCP Server thread](https://discourse.mcneel.com/t/rhino-mcp-server/216568); [100 models](https://dev.to/allelishi/i-built-100-rhino-models-almost-on-autopilot-with-rhinomcp-x-claude-code-2gad)). Grasshopper authoring works for small-to-medium graphs but trips on "multiple components with the same name" ([100 Grasshopper programs](https://medium.com/@allelishi/i-wrote-100-grasshopper-programs-with-rhinomcp-claude-code-f8d493160260)). The robust pattern on either platform is therefore one `run_python`/`execute` call that builds the whole maze from data, not hundreds of `create_object` calls — and that pattern is exactly what a script-first, file-first workflow produces.

## DXF, not SVG, is the carrier that survives import into either program

Your app's SVG-with-named-layers output is the weakest link in either pipeline, and the problem is worse in Fusion. Fusion's Insert SVG treats unitless pixels at 96 dpi (users apply a **3.779528×** correction for Inkscape files and 1.333× for Illustrator's 72 dpi), imports "as sketch curves" that arrive fixed/locked, ignores stroke width ("all you see is the centerline"), flattens all groups and layers into **one sketch**, has a reported bug where the dialog's scale is applied twice, and chokes when a single sketch receives ~18,000 curves because "Fusion's sketch solver is just not going to handle this much info in one sketch" ([SVG scale thread](https://forums.autodesk.com/t5/fusion-360-design-validate/svg-scale-is-wrong/td-p/6560352); [SVG import handling](https://forums.autodesk.com/t5/fusion-support-forum/svg-import-handling/m-p/9744571/highlight/true); [double-scale bug](https://forums.autodesk.com/t5/fusion-support-forum/fix-dimensions-of-imported-svg/m-p/12481033); [complex SVG performance](https://forums.autodesk.com/t5/fusion-support-forum/complex-svg-dxf-alternatives-for-performance/td-p/12508894)). Fusion has no SVG *export* at all. DXF behaves far better: the Insert DXF dialog lists the file's layers and offers "One Sketch per Layer", the API's `DXF2DImportOptions.isSingleSketchResult` defaults to one sketch per layer, and units are selectable — though with no `$INSUNITS` header Fusion defaults to **centimetres**, so a millimetre file lands 10× too large ([Insert DXF](https://help.autodesk.com/cloudhelp/ENU/Fusion-Model/files/SLD-INS-DXF.htm); [DXF2DImportOptions](https://help.autodesk.com/cloudhelp/ENU/Fusion-360-API/files/DXF2DImportOptions.htm); [DXF 10× thread](https://forums.autodesk.com/t5/fusion-design-validate-document/imported-dxf-file-is-x10-scaled/td-p/6025181)). Splines are linearised on DXF import (one user saw ~20 curves become ~700 segments), so machinable geometry should be emitted as `LWPOLYLINE` and `ARC` entities, never `SPLINE` ([DXF import sketch problem](https://forums.autodesk.com/t5/fusion-support/dxf-import-sketch-problem/td-p/10613289)).

Rhino 8 handles both formats natively on Windows and Mac — its format index lists 3MF, AI, DXF, PDF, SVG and STEP for import *and* export ([Rhino 8 format index](https://docs.mcneel.com/rhino/8/help/en-us/fileio/_index_of_import_export_file_types.htm)). Its SVG importer offers "Retain grouping", "Group multi curve paths" and "Import filled objects as Curves/Hatches/Trimmed planes", maps one `viewBox` unit to one model unit (ignoring `width`/`height`, a behaviour McNeel logged as bug RH-84096), and had a closed-path arc-seam bug fixed only in **Rhino 8 SR34** ([SVG help](https://docs.mcneel.com/rhino/8/help/en-us/fileio/scalable%20vector%20graphics_svg_import_export.htm); [viewBox thread](https://discourse.mcneel.com/t/svg-import-doesnt-respect-width-height/124987); [RH-84096](https://discourse.mcneel.com/t/svg-scaling-units/146492); [RH-96250](https://discourse.mcneel.com/t/bug-svg-import/219824)). Whether `<g id="walls">` becomes a Rhino *layer* rather than a *group* is undocumented — a five-line Python script can move each group to a layer named after its `id`, but DXF needs no such step: Rhino's DWG/DXF importer preserves layers, honours model units, and keeps arcs as arcs ([Rhino 8 DWG/DXF help](https://docs.mcneel.com/rhino/8/help/en-us/fileio/autocad_dwg_dxf_import_export.htm)). The DXF writer is trivial to add headlessly: **ezdxf 1.4.4** (May 2026) writes DXF R2018 with layers, `LWPOLYLINE` bulge arcs (bulge 1 = semicircle) and `ARC` entities, and because DXF R12/R2000 ASCII is a simple text format, a hand-rolled writer in `index.html` is equally feasible ([PyPI ezdxf](https://pypi.org/project/ezdxf/); [ezdxf LWPolyline tutorial](https://ezdxf.readthedocs.io/en/stable/tutorials/lwpolyline.html)).

Between the two programs, exchange is asymmetric. Fusion lists Rhino `.3dm` as an importable format but **"all license types except Personal Use"**, and even then "Fusion only imports surface and body information, not curve information" from Rhino files — so a rhino3dm-generated `.3dm` is never the way into Fusion ([Fusion supported formats](https://help.autodesk.com/cloudhelp/ENU/Fusion-Import/files/TPD-SUPPORTED-FILE-FORMATS.htm); [Rhino→Fusion curves](https://forums.autodesk.com/t5/fusion-360-design-validate/exporting-from-rhinoceros-to-fusion-360/td-p/5972714)). Rhino cannot read `.f3d` at all; the only route is to open the file in Fusion and export STEP ([f3d into Rhino](https://discourse.mcneel.com/t/fusion-360-f3d-files-into-rhino/100088)). STEP is the right solid carrier in both directions (McNeel's advice: "always start with STEP"; Fusion's STEP import is available on all tiers including Personal Use after Autodesk's September 2020 reversal), with the caveat that Fusion-exported STEP arrives in Rhino as a block that `ExplodeBlockToLayers` can split per body ([McNeel import guidance](https://discourse.mcneel.com/t/best-import-format-from-non-rhino-to-nurbs-rhino/124100); [Fusion STEP import block](https://discourse.mcneel.com/t/import-file-from-fusion-360/96434); [STEP export stays](https://www.autodesk.com/products/fusion-360/blog/changes-to-fusion-360-for-personal-use/)). For 3D-printed and ball mazes both programs export STL and 3MF, and an agent can bypass both: **trimesh 5.1.1** (Oct 2026) exports STL/3MF and build123d/CadQuery export exact solids ([PyPI trimesh](https://pypi.org/project/trimesh/); [PyPI build123d](https://pypi.org/project/build123d/)).

Three exporter rules follow for `index.html`. Emit **closed wall-outline polygons** (offset the centreline by half the wall thickness your `wallFrac` already encodes), because every CAM package pockets closed regions and Fusion discards stroke width. Write `$INSUNITS = 4` (mm) in the DXF header and, if SVG is kept, declare `width="…mm" height="…mm"` with a matching millimetre `viewBox`, absolute path commands and no `transform` attributes. And give every layer a **distinct stroke colour** (`boundary` ≠ `walls`), because LightBurn and Carbide Create assign cut operations by colour, not by layer name ([LightBurn basic usage](https://docs.lightburnsoftware.com/BasicUsageEssentials.html); [Carbide Create layers](https://community.carbide3d.com/t/importing-layers-into-carbide-create/90621)).

## Fusion's scriptable CAM is real, but a 2.5D maze does not need it

Fusion's CAM is the one capability Rhino genuinely lacks, and it is scriptable end to end. The API exposes `CAM.setups`, `Operations.createInput('pocket2d')`/`'contour2d'`, `CAM.generateToolpath` and — since `CAM.postProcess` was "retired in version September 2025" — `NCProgram.postProcess` to emit machine-specific G-code; `CAMManager.libraryManager` reaches the post and machine libraries, which include Autodesk's GRBL post "for both CNC routers and laser machines" and community posts for Onefinity/Buildbotics ([CAM.postProcess](https://help.autodesk.com/cloudhelp/ENU/Fusion-360-API/files/CAM_postProcess.htm); [NCProgram.postProcess](https://help.autodesk.com/cloudhelp/ENU/Fusion-360-API/files/cam_NCProgram_postProcess.htm); [CAM.generateToolpath](https://help.autodesk.com/cloudhelp/ENU/Fusion-360-API/files/cam_CAM_generateToolpath.htm); [GRBL post](https://www.autodesk.com/products/fusion-360/blog/fusion-360-grbl-post/)). Community code shows the 2D pocket flow (`createInput('pocket2d')`, assign tool, `parameters.itemByName('pockets')` → `createNewChainSelection()` → `applyCurveSelections()`), with the warning that parameter names differ per strategy and a planar-face selection once crashed Fusion ([pocket2d thread](https://forums.autodesk.com/t5/fusion-api-and-scripts/how-to-add-pocket-operation-from-simply-closed-profile/td-p/11903594)). Post processors are JavaScript `.cps` files and the post engine has a CLI (`post config.cps intermediate.cnc --property name value`), but the `.cnc` intermediate can only come from Fusion, so the CLI re-posts rather than removing Fusion from the loop ([post usage reference](https://cam.autodesk.com/posts/reference/usage.html)). In Autodesk's own Compute MCP demo an agent built mould plates and generated face, adaptive and parallel toolpaths "in about 6.5 seconds" ([Compute MCP](https://www.autodesk.com/products/fusion-360/blog/fusion-compute-mcp/)). All of this is GUI-bound on the desktop and beta-plus-subscription in the cloud, and every CAM-capable community server (faust-machines, tbrito88, BJam's CLI) warns that toolpaths must be simulated and human-reviewed before any cut.

If you drop to **Fusion for Personal Use**, the CAM you need survives in reduced form. Autodesk's 2020 change kept "2, 2.5 and 3 axis milling", toolpath simulation, scripts/add-ins and STEP export, but removed automatic tool changes ("post one file per tool"), capped rapids at cutting feedrate, removed 3+2/multi-axis and probing, and imposed a **10 active-document** cap; the current comparison page still lists "limited CAM" and the under-$1,000/year eligibility rule, and 2024–26 forum threads confirm the restrictions persist ([Personal Use changes](https://www.autodesk.com/products/fusion-360/blog/changes-to-fusion-360-for-personal-use/); [compare page](https://www.autodesk.com/products/fusion-360/personal); [10-document limit](https://www.autodesk.com/products/fusion-360/blog/january-2021-product-update-whats-new/)). Makers describe the effect concretely: Fusion "removes all G0 rapid moves between cuts, replacing them with G1 straight moves at the feed rate of the previous cut loop", which lengthens cycle time but is fixable with community post patches ([Carbide 3D community](https://community.carbide3d.com/t/understanding-the-loss-of-rapids/26422)). An Autodesk engineer confirmed in 2019 that add-ins work on the free plan, and a 2026 community bridge states "a free personal licence is sufficient", so a self-written localhost bridge remains viable even if the official MCP is not ([add-ins on free plan](https://forums.autodesk.com/t5/fusion-api-and-scripts-forum/add-ins-missing/m-p/9728436); [ndoo bridge](https://github.com/ndoo/fusion360-mcp-bridge)).

Rhino has **no built-in CAM**, and the in-Rhino options are expensive and Windows-only: MecSoft's RhinoCAM 2026 runs **US$595 (MILL Xpress), $1,500 (Standard), $2,500 (Expert, +$400/yr maintenance), $5,000 and $10,000**, with no public scripting API in the pages seen; MadCAM's standalone price was not found ([RhinoCAM MILL Xpress](https://mecsoft.com/shop/product/rhinocam-mill-xpress/); [RhinoCAM Expert](https://mecsoft.com/shop/product/rhinocam-expert/); [MecSoft shop](https://mecsoft.com/shop/)). But the maze workflow does not need CAM *inside* the CAD program, because the geometry is already 2D vectors. **Kiri:Moto** is "completely open source and free for use without restriction", runs locally from npm (`gs-app-server --debug` → `http://localhost:8080/kiri`), auto-extrudes imported SVG (depth via a `data-km-extrude` attribute), offers pocket/outline/contour/drill operations with tabs, and exports GRBL-style G-code with editable header/footer/tool-change macros — the only CAM here an agent could plausibly drive end to end via browser automation ([grid-apps](https://github.com/GridSpace/grid-apps); [Kiri:Moto CAM](https://docs.grid.space/kiri-moto/CAM/); [SVG import](https://forum.grid.space/t/kiri-moto-svg-import-improvements/773)). **Carbide Create Pro** unlocks G-code export for "any machine that runs GRBL" at **US$120/year or $360 perpetual**; **Estlcam** is 49 €/US$59; **LightBurn Core** is US$99 for G-code lasers; VCarve Desktop/Pro are $349/$699 ([Carbide Create Pro](https://carbide3d.com/carbidecreate/pro/); [Estlcam](https://www.estlcam.de/estlcam.php); [LightBurn store](https://lightburnsoftware.com/collections/lightburn); [VCarve pricing](https://simplytechnologies.xyz/vcarve-pro-canada-guide-2/)). Ranked by how much of the pipeline an agent can automate for a pocketed maze on a GRBL/Onefinity router: app → DXF/SVG → Kiri:Moto first; app → DXF → Carbide Create Pro/Estlcam/VCarve second; app → DXF → Fusion add-in → G-code third (fully scriptable but GUI-hosted, and the only route that also yields a solid for simulation); and via Rhino only when you want Grasshopper regeneration or 3D visualisation, since Rhino must hand off to one of the above anyway.

The paradigm difference you acknowledged — Fusion's history-based parametric solids versus Rhino's direct NURBS modelling with Grasshopper for parametrics — matters less for mazes than it would for a product design, because **your app is already the parametric model**: `cellSize`, `wallFrac`, `toolDiamMm` and the `{minP, minW, minC}` constraint cascade live in `S`, and `doGenerate()` re-snaps doors by millimetre position on every regeneration. In Fusion, imported SVG/DXF sketch geometry arrives "Fixed" and imported splines "can't be edited the same way", so the timeline cannot drive a maze's wall thickness anyway; changing a parameter means re-inserting the DXF and hoping dependent extrude/pocket features still resolve ([working with SVG](https://forums.autodesk.com/t5/fusion-design-validate-document/working-with-svg/m-p/6847510)). Where each program earns its keep is at the edges: Fusion for a filleted ball-maze channel with floor radii simulated against real tooling on the same model; Rhino and Grasshopper for exploring concentric/polar or curved-wall variants with NURBS arcs and clean multi-format export. Headless fillets, if you need them without either GUI, come from build123d/OpenCascade, not rhino3dm ([PyPI build123d](https://pypi.org/project/build123d/)).

The cost side is lopsided. Fusion commercial lists at **US$85/month, $680/year or $2,040/3 years**, with extensions at roughly $595–$1,465 each per year ([Autodesk subscription FAQ](https://www.autodesk.com/solutions/autodesk-fusion-subscription-faq); [subscription types](https://www.autodesk.com/products/fusion-360/blog/fusion-subscription-types/)). Your Rhino 8 licence is perpetual ("all purchased licenses are permanent and do not expire … There are no maintenance fees"), covers Windows and Mac on one Cloud Zoo key, and already entitles you to the Rhino 9 Beta that McNeel describes as feature-complete with weekly builds; when Rhino 9 ships — unannounced but imminent — a paid upgrade (historically ~$595 with a launch discount) is optional, since the official MCP plugin targets Rhino 8 ≥ 8.19 ([Rhino sales terms](https://www.rhino3d.com/en/sales/europe/United_Kingdom/all/); [Rhino store](https://www.rhino3d.com/store); [Rhino 9 Beta](https://discourse.mcneel.com/t/help-shape-rhino-9-the-beta-is-here/220246); [upgrade policy](https://discourse.mcneel.com/t/new-licence-and-rhino-wip/218202)). So the choice is $680/year for Fusion's unique capabilities versus $0 marginal for Rhino's — and Rhino's unique capabilities (open file format, CLI, free local Compute, free official MCP) are the ones a coding agent uses most.

## Conclusion

The question "which CAD program is more interoperable with Claude Code" turns out to have a structural answer rather than a feature-count answer. Fusion's agent story is strong but *gated* — by a subscription, by a GUI that must be open, or by a metered cloud — whereas Rhino's is *open*: the file format has a free MIT writer that runs in a browser tab, the desktop has a real CLI, and the vendor's own MCP server is free software that names Claude Code in its docs. For an agent, openness compounds: the same Python that writes a `.3dm` in a Linux container today runs unchanged inside Rhino's ScriptEditor, via `rhinocode`, or through any MCP server's `run_python` tool tomorrow. Nothing in Fusion's ecosystem offers that continuity, because `.f3d` can only be born inside Fusion.

The deeper implication for your project is that the maze app, not either CAD package, should be the system of record. Once `index.html` emits layered DXF and `.3dm` alongside SVG, Rhino, Fusion Personal Use, Kiri:Moto, Carbide Create and LightBurn all become interchangeable *consumers*, and the November renewal stops being a strategic decision at all — it becomes a question of whether $680 a year buys enough convenience in the one step (CAM with simulation) that a free tool handles adequately for 2.5D work. Spend the remaining paid weeks proving that to yourself with the bake-off, and let the data make the call.
